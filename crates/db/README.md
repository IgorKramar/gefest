# `hef-db` — прослойка доступа к Postgres

Здесь живут SQL-запросы, миграции и доступ к базе. Это единственный крейт,
где есть `query!` и `migrations/`.

## Цикл sqlx

Гефест использует макросы `query!`/`query_as!`, которые проверяют SQL **во
время компиляции**. Чтобы это работало без базы под рукой, sqlx хранит
метаданные запросов в каталоге `.sqlx/` в корне репозитория — он
коммитится.

Отсюда два разных режима, которые легко перепутать:

| Команда | Нужна база? | Что делает |
|---|---|---|
| `cargo build`, `cargo test` | **нет** | читают готовый `.sqlx` |
| `mise run sqlx:prepare` | **да** | перегенерирует `.sqlx` по живой схеме |
| `mise run sqlx:check` | **да** | проверяет, что `.sqlx` не разошёлся с запросами |

`SQLX_OFFLINE=true` выставляется **только в окружении CI** — там, где идут
сборка и тесты. В репозиторный `.env` его класть нельзя: это ломает сам
`prepare`, который обязан подключиться к базе, чтобы выполнить свою работу.

## Красный `prepare --check`: что делать

Проверка краснеет, когда `.sqlx` разошёлся с реальными запросами — обычно
потому, что запрос поменяли, а метаданные не перегенерировали.

**Сначала определите, кто вы в этой ситуации.**

**Агент в контейнере задачи.** У вас нет ни базы, ни секретов к ней
(ADR-0006) — это не упущение, а устройство периметра. Честного пути до
зелёного у вас здесь нет. Зафиксируйте отказ и эскалируйте владельцу; не
пытайтесь добыть DSN и не обходите проверку способами из раздела ниже.

**Владелец.** По шагам:

1. Поднимите локальную dev-базу и примените к ней миграции.
2. Экспортируйте `DATABASE_URL` на **локальную** базу.
3. `mise run sqlx:prepare`
4. Убедитесь, что `mise run sqlx:check` зелёный.
5. Закоммитьте изменения в `.sqlx/` вместе с изменением запроса — одним
   коммитом, иначе следующий прогон покраснеет снова.

## Чего делать нельзя

Каждый пункт ниже выглядит как решение проблемы. На деле это способ
получить зелёную проверку при мёртвой гарантии — что хуже отсутствия
проверки: без сторожа рассинхрон хотя бы виден, с обойдённым — сертифицирован
зелёным.

1. **Править файлы в `.sqlx/` руками.** Метаданные перестают отражать
   реальные запросы. Проверка зелёная, проверять нечего.
2. **Ставить `SQLX_OFFLINE=true` в `.env` или с `force = true` в
   `.cargo/config.toml`.** Ломает сам `prepare`: команде, которая обязана
   сходить в базу, объявляют, что базы нет.

   Репозиторное умолчание `SQLX_OFFLINE=true` в `.cargo/config.toml` при этом
   **правильно и стоит там намеренно** — но именно без `force`. Причина:
   `cargo sqlx prepare` сам выставляет дочернему процессу `SQLX_OFFLINE=false`,
   и не-force значение из конфига ему уступает. С `force = true` уступки не
   происходит, `prepare` уходит в офлайн, а `prepare --check` начинает сверять
   кэш сам с собой — зелёный всегда.
3. **Уходить с `query!` на нетипизированный `sqlx::query`.** Исчезает
   compile-time проверка SQL — ровно та гарантия, ради которой выбрана sqlx.
   Код формально проходит сторожа, не будучи проверенным.
4. **Подставлять в `DATABASE_URL` не локальную базу.** Граница C-2
   (ADR-0010): в этом runbook участвует только локальная dev-БД. DSN
   staging или прода не попадает ни в `DATABASE_URL`, ни в `.env`, ни в
   вывод команды, ни в описание PR или issue — включая просьбы о помощи.

## Интерим-регламент: SQL меняет владелец

**До готовности брокера ресурсов (GF-2) SQL-запросы в этом крейте меняет
только владелец.**

Причина — та же, что и в разделе выше: агенту негде взять живую базу, а
значит, нет честного пути перегенерировать `.sqlx`. Регламент сужает круг
осознанно, вместо того чтобы ждать, что агент «как-нибудь справится», и
получать обходы.

**Условие снятия названо:** брокер ресурсов (ADR-0006) выдаёт контейнеру
задачи dev-БД клоном шаблона со схемой Гефеста, `mise run sqlx:prepare`
берёт DSN из комплекта — и ограничение снимается. Сужение автономии без
условия снятия было бы не регламентом, а дырой.

## Сторож `prepare --check` в CI

Его пока **нет**, и это решение, а не забывчивость.

Миграции и тесты появились, service-контейнер в CI поднимается — но макросов
`query!` в коде по-прежнему нет: прослойка использует функцию `sqlx::query()`,
которой кэш запросов не нужен. Проверять `prepare --check` сейчас нечего.

Доменные запросы придут с раннером (GF-2), и вместе с ними — макросы, каталог
`.sqlx` и этот шаг. Чтобы это не зависело от чьей-то памяти,
стоит растяжка `mise run guard:sqlx-step`: она краснеет, если макросы
запросов появились, а шага `prepare --check` в CI всё ещё нет.

Принцип, по которому принято это решение:
[«Сторож против невозможности»](../../docs/solutions/best-practices/storozh-protiv-nevozmozhnosti.md).
