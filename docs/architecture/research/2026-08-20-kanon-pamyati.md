# Discovery: канон памяти Гефеста (D-8; C-Н5, Ф3)

- Дата: 2026-08-20
- Масштаб цикла: **deep** (область в открытых вопросах ARCHITECTURE.md; первое решение в области «память»; новая внешняя зависимость-кандидат EverOS)
- Статус: раунд 1, ожидаются ответы владельца
- Связь: decision-map D-8; ADR-0001 (Ф3), ADR-0002 (фиксация в репо); requirement C-Н5 (уточнён владельцем трижды 2026-08-20)

## 1. Проблема, как я её понял

C-Н5 требует: **один источник истины — общая система памяти; личные памяти агентов согласуются с ней; vault Obsidian выводится целиком; привычки покрываются (С7)**. Сегодня «память» команды размазана по шести слоям с разными хозяевами, форматами и механизмами доставки в контекст агентов. Нужно решить: что есть канон в Гефесте, как в него пишут, как из него читают (в т.ч. агенты при старте сессии), как «поднимаются» личные памяти, и место EverOS в этой картине.

**Явное допущение:** механика памяти Claude Code (авто-память в `~/.claude/projects/<cwd>/memory/`, MEMORY.md-индекс, инжекция в системный промпт; CLAUDE.md-слои; SessionStart-хуки) — фиксированная данность harness, менять можем только то, *что* в неё кладём и *откуда*.

## 2. Инвентаризация текущих слоёв (факты, 2026-08-20)

| Слой | Объём | Хозяин | Как попадает к агенту |
|---|---|---|---|
| Авто-память Claude Code | 11 каталогов по cwd; крупнейшие: erp-ir 17 файлов/67 КБ, ir-gsm 9/17 КБ, vaults-work 6/11 КБ | каждая сессия сама | MEMORY.md инжектится harness-ом в контекст своего cwd |
| CLAUDE.md-слои | глобальный 3,6 КБ + vault 25 КБ (+ по репозиториям) | владелец/ПМ | инжекция harness-ом |
| База знаний vault `30-resources` | 35 статей, 384 КБ | ПМ/агенты через `ad doc-write` | **SessionStart-хук инжектит весь индекс с аннотациями** в каждую сессию vault-контура |
| `.remember/` (плагин) | 1,3 МБ (дневники, recent, archive, core-memories) | плагин remember | SessionStart-хук инжектит свежие срезы |
| `documents` в agent-dashboard | тексты vault в Postgres, русский FTS, ревизии | коллектор/панель | агенты — через CLI/API по запросу |
| learnings-процесс | ce-compound → docs/solutions (ir-gsm) или статья в 30-resources | процесс `/ir-task` | через слои выше |

Наблюдения из инвентаризации:
- **Личные памяти фрагментированы по cwd**: у одного агента в worktree — своя память, в основном репо — другая; память worktree-каталогов (ad-11, ad-12…) умирает вместе с worktree — «подъёма» из них нет.
- **Дублирование уже трёхслойное**: статья 30-resources живёт файлом в vault, строкой в `documents` (БД) и в инжекте хука.
- Инжекция базы знаний — «всё в каждую сессию»: 35 аннотаций на старте; при росте до сотен статей упрётся в токены.

## 3. Функциональные требования (сценарии)

- **П1. Recall при старте.** Агент начинает задачу и получает релевантные знания (правила, ловушки, learnings) — сегодня «всё скопом», целевое — не хуже по полноте, лучше по точности/токенам.
- **П2. Запись выученного.** Агент/владелец фиксирует learning один раз — он попадает в канон, доступен всем, с автором и датой.
- **П3. Подъём личной памяти.** Ценная запись из авто-памяти сессии (сейчас умирает с worktree) поднимается в канон — автоматически или ритуалом.
- **П4. Выгрузка канона вниз.** Локальные механизмы (CLAUDE.md-фрагменты, memory-файлы ролей) генерируются из канона — не редактируются руками в обход.
- **П5. Владелец читает/правит** канон из панели Гефеста: wiki-линки, бэклинки, русский поиск (С7).
- **П6. Журналирование дней** (функция .remember) — куда-то переезжает или сознательно остаётся плагином.

## 4. Атрибуты качества

- Долговечность: канон не теряется никогда (наравне с журналом — бэкапы Гефеста).
- Консистентность: одна правда на знание; производные слои могут отставать, но расхождение видимо.
- Токен-бюджет recall: инжекция на старте ограничена (сегодня ~единицы КБ на слой; рост базы не должен линейно раздувать каждый старт).
- Приватность: карточки людей и рабочий контекст — только свой Postgres/диск (после D-14 — никакого стороннего облака).
- LLM-бюджет фоновых процессов (консолидация, эмбеддинги): только бесплатный OpenRouter либо локально; подписка — исполнителям.

## 5. Ограничения

- Механика Claude Code фиксирована (см. допущение). Хуки SessionStart — легальная точка инжекции; MCP — легальная точка recall-by-need.
- ADR-0002: канон по Гефесту — в репо/БД Гефеста; vault не используется.
- Один оператор (F7): слой памяти не должен добавить второй «сервис, который надо нянчить».
- Схема данных Гефеста (D-2) ещё не принята — это шанс: канон проектируется вместе с ней, а не поверх.

## 6. Prior art

- `documents` + `document_revisions` agent-dashboard (Postgres, русский FTS, ревизии, выгрузка в файлы) — ближайший работающий прототип канона.
- 30-resources + SessionStart-хук — работающий прототип «канон → инжекция», с известным пределом по токенам.
- DSH: session store + append-only лог; памятные плагины экосистемы (Graph Memory, Mnemon, Engramory — README-уровень).
- yao: генерация auto-memory файлов для Claude Code с правилом «MEMORY.md не перезаписывать» (docs/06 §1.6) — готовый образец механики «выгрузки вниз».
- **EverOS** — кандидат-зависимость: 12,2k ⭐, «переносимый Markdown-слой памяти»; два исследования запущены (веб + исходники), результаты лягут в research-фазу.
- Правило CLAUDE.md «чужая находка несётся с областью наблюдения» и статьи 30-resources — готовая редакционная политика канона.

## 7. Силы

- **F-П1. Токены против полноты**: «всё в каждый старт» не масштабируется; recall-by-need (поиск/MCP) экономит токены, но агент не знает, чего не знает — правила и ловушки работают именно потому, что инжектятся навязчиво.
- **F-П2. Двусторонность — самая дорогая часть C-Н5** (зафиксировано в discovery консолидации): вниз — генерация, вверх — подъём; автоматический подъём рискует замусорить канон, ритуальный — не выполняться (урок 18.08 про исчезающие процессы).
- **F-П3. Внешняя зависимость против F7**: EverOS может дать готовый слой, но добавляет сервис, релизный темп и формат, которые нянчит один человек; урок yao (лицензия, темп) свеж.
- **F-П4. Канон в БД против «файлы удобны агентам»**: агенты и harness едят файлы (CLAUDE.md, memory); владелец хочет панель и поиск; двусторонняя генерация «БД ↔ файлы» уже отработана в agent-dashboard в одну сторону.
- **F-П5. Схема D-2 проектируется сейчас** — решение о памяти либо въезжает в неё, либо навсегда останется пристройкой.

## 8. Открытые вопросы (по приоритету)

1. **Скоуп канона.** Что входит: learnings/правила/ловушки (30-resources), процессные CLAUDE.md-правила, карточки людей, дневники .remember, память ролей (11 именных), справочники? Назови, что точно внутри и что точно снаружи.
2. **Политика recall.** Сохраняем «навязчивую инжекцию» ядра (правила+ловушки всегда в контексте) + поиск для остального? Или всё через recall-by-need? Где граница «всегда в голове» / «найдёт при нужде»?
3. **Подъём личных памятей** — автоматика или ритуал? Вариант-гибрид: хук на конец сессии предлагает кандидатов, ПМ/владелец утверждает. Кто редактор канона?
4. **EverOS a priori**: если research покажет зрелость — готов ли ты на внешнюю зависимость в самом сердце знаний (против F7 и урока yao)? Или EverOS заранее в статусе «донор идей», и цикл выбирает только между «своё в Postgres» и «своё в файлах+индекс»?
5. **Дневники .remember** — входят в канон (и тогда их пишет Гефест), или остаются личным плагином владельца вне скоупа?
6. **Память ролей** (Теодор/Михаил/Григорий…): роль должна помнить своё между задачами и машинами (после переезда на сервер) — это требование канона или остаётся локальной механикой Claude Code?

### Предложения исполнителя (запрошены владельцем)

- **Р-1 (граница инжекции/поиска).** Трёхслойная модель: (а) **ядро** — правила, ловушки, процессные инструкции — инжектится всегда, с жёстким бюджетом (ориентир ≤ 8–12 КБ суммарно), состав курирует мастер-агент: попадание в ядро — редакционное решение, а не автоматизм; (б) **индекс** — аннотации остального канона (как сегодня аннотации 30-resources) — инжектится всегда, тексты по запросу; (в) **тело** — полные тексты, дневники, карточки — только recall-by-need (поиск/MCP/CLI). Рост базы раздувает только индекс (строка на статью), не ядро. Финализация — в Design.
- **Р-2 (дневники)** — см. вопрос 5.

### Новые ограничения

- **C-П1.** Редактор канона знаний — мастер-агент: подъём гибридный (хук предлагает кандидатов из личных памятей/сессий → мастер-агент утверждает/правит/отклоняет; след решения остаётся).
- **C-П2.** Память ролей (11 именных) — first-class скоуп канона: роль помнит своё между задачами, worktree и машинами.

### Уточнение сил

- **F-П6 (новая).** Механика памяти Claude Code скоупится по **cwd**, а требование C-П2 — по **роли**: один агент работает в разных worktree, роль живёт на разных машинах. Нужен мост «роль → cwd» (генерация memory-файлов роли в каждый рабочий каталог из канона — образец: yao genfile-подход, docs/06 §1.6, включая правило «MEMORY.md не перезаписывать»). Это самая механически тонкая часть решения.
- F-П2 подтверждена ответом 3: гибрид с мастер-агентом — ровно баланс «автоматика не мусорит, ритуал не забывается».

### Вердикт раунда 2

Материальных противоречий нет; П-П1 — терминологическое уточнение скоупа, принято без спора. Продолжаем по плану deep: research (ожидается разбор исходников EverOS) → Design. Открытых вопросов к владельцу не осталось; Р-1/Р-2 подтверждаются на гейте Decide.
