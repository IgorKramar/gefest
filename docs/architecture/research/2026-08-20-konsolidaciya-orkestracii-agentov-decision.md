## 1. Выбранная альтернатива

**B: собственный тонкий оркестратор (эволюция agent-dashboard) — спроектированный «на плечах» yao и DSH.**

Три составляющие:

1. **Ф0 — немедленно:** доставка команд переводится на spawn/resume-механику: раннер владеет процессами `claude -p --resume` (stream-json), состояние доставки подтверждаемо. Честный объём — **8–12 инженерных дней** (roast H-4): это новый супервизор процессов, а не «фикс» (переподхват после рестарта раннера, идемпотентность доставки, парсинг stream-json, различение «прервано» от «завершено»).
2. **Ф0.5 — архитектурная фаза (требование владельца, ред. 2):** прежнее «делалось на ходу из потребности, без архитектуры и ориентиров» заменяется проектированием с ориентирами. Внимательное изучение устройства yao и DSH (изнутри, по исходникам — клоны в `reference/`) → **карта заимствований** (что берём как идеи: append-only session log как единственная истина и производная история — DSH; машина состояний доставки; stream-парсинг и resume-механика Claude Code — yao `agent/sandbox/v2/claude/`; модель персистентных песочниц — yao; DAG задач с CAS-ревизиями и mailbox — DSH `agent-team`; слоты/расширяемость UI — DSH client) → ARCHITECTURE.md и ADR-серия целевой системы. Ничего из чужого кода не тянем как зависимость — только архитектурные решения.
3. **Пилот yao отменён** (см. Историю редакций). yao и DSH — доноры идей; их клоны остаются в `reference/` как учебный материал.

### Различение ToS-рисков (roast C-1, зафиксировано)

- **Путь B — аргументируем:** свой раннер вызывает официальный Claude Code CLI в его документированном headless-режиме; подписочная авторизация используется самим продуктом Anthropic на машине владельца. Остаточный риск (формализация позиции по серверному headless — roast F-7) принят владельцем; граница пересмотра — §4.
- **Путь A был бы нарушением:** креды подписки внутри стороннего продукта — запрещено Consumer Terms §2–3. Возврат к yao возможен только через границы §4.

## 2. Почему это решение

- **Roast-кластер 1 снял выбор:** без подписки путь A требует API-токенов (нарушает C-Н1) либо не-Claude исполнителей (нарушает ответ №1) — пилот проверял бы то, чем нельзя пользоваться.
- **Спайки S1a/S2 открыли дверь B:** подписочный OAuth работает в контейнере (монтирование одного файла), параллельные headless-сессии работают, лимиты читаются программно. Все примитивы B — официальные функции Claude Code.
- **Асимметрия обратимости:** B (своя база + раннер + UI) дёшево конвертируется в «наша модель задач поверх зрелой платформы», когда DSH/yao дозреют и легализуются (roast F-9); обратное — нет.
- **Процесс сохраняется без адаптации:** `/ir-task`, hooks, worktrees, «готово = мерж + зелёный пайплайн», детекторы расхождений — всё уже смоделировано в схеме agent-dashboard; платформа не диктует чужую модель задач.
- **Требование владельца «с умом» (ред. 2):** причина кривизны текущей панели — не стек, а отсутствие архитектуры; Ф0.5 лечит причину, а не симптом.

## 3. Что мы отдаём (принятые минусы)

- 4–7 недель чистой разработки до паритета по С1–С7; при реальном темпе «1–2 ч/день между основными задачами» — 2–4 календарных месяца (roast H-6; календарный множитель назван честно).
- Bus-factor 1 и норма обслуживания: дефекты панели класса «истина врёт» (статусы, доставка, устаревшая сборка) приоритетнее фич любых проектов (roast F-4 — принято как правило).
- Отказ от «бонусов» готовых платформ: VNC-песочницы, готовые мобильные клиенты, интеграции. **Граница «тонкого» B (roast F-9):** B никогда не строит — собственные VNC/desktop-песочницы, мультимодельных агентов-исполнителей, свой чат-клиент общего назначения, собственный CI. Утолщение — только отдельным решением через ADR.
- Остаточный ToS-риск серверного подписочного headless — принят (см. §1); негативная формализация ударит по бюджетной модели (граница §4).

## 4. Границы пересмотра решения

Триггеры **активные, не пассивные** (roast F-1): при принятии ADR заводится квартальная календарная задача «ревизия границ пересмотра» в панели; паритет С1–С7 проверяется по чек-листу §7.

1. **DSH дозревает** (durable-интеграция Claude Code: стрим + resume + видимость в UI + auth в Web UI) — пересмотр в пользу платформы; знания собраны в docs/03–04.
2. **yao легализуется** (одобрение Anthropic / появляется бюджет на API-токены / yao даёт официальный подписочный путь) — пересмотр в пользу A; знания в docs/06 и reference/yao.
3. **Anthropic формализует запрет** серверного подписочного headless (ToS/техблок) — пересмотр бюджетной модели C-Н1 и схемы исполнителей.
4. **Второй человек-оператор** — пересмотр F7; схема данных готова заранее (поле автор/адресат — §5).
5. **Причина для кубера** (второй хост, автоскейл) — цель развёртывания меняется с compose (резолюция П-1).
6. **Через 3 месяца от старта Ф1 паритет по чек-листу §7 не достигнут** — ревизия с явными исходами: сузить скоуп С-сценариев / заморозить фичи и дожать «истина врёт»-класс / вернуться к рынку платформ (границы 1–2).

## 5. Операционные последствия

- **Серверный хост** (тот же, где AFFiNE, или новый — **решение до конца Ф1, по умолчанию тот же**; roast F-6 — у отложенного есть дедлайн и умолчание): docker-compose, systemd, бэкапы Postgres.
- **Периметр (принцип, roast C-3):** панель недоступна из публичного интернета — доступ только через VPN/mesh (WireGuard/Tailscale); публичный HTTPS-endpoint возможен только отдельным решением с компенсациями (2FA, аудит входов). PWA работает поверх VPN.
- **Матрица секретов (roast C-2) — обязательный артефакт Ф1:** креды Anthropic, gh/glab-токены (scoped per-репо для агентов, не общий токен владельца), OpenRouter-ключ, пароли БД × (где хранится, кто читает, как ротируется, как обнаруживается утечка). `~/.claude/.credentials.json` — серверный секрет; проверка «креды читаемы + `claude -p ping` отвечает непустым» — в health-check раннера с первого дня (ловушка S1b: молчаливый выход с кодом 0; сегодня усугублена DEVNULL в runner.py — roast H-2).
- **Уведомления (roast H-7):** внешний heartbeat раннера (healthchecks.io/Telegram) — в объёме Ф0; процедура консервации на отпуск (выключить раннер, убрать креды с хоста) — полстраницы в runbook.
- **Бэкапы (roast H-3):** pg_dump по крону + выгрузка вне хоста + **проверенный restore** — предусловие вывода vault (§7); git-выгрузка vault остаётся включённой до этого дня.
- **Supabase:** вывод данных (миграция + удаление проекта, закрывает и бэкапы вендора) — **до конца Ф1, по умолчанию свой Postgres в compose** (roast C-5, F-6).
- **Прослойка CLI (roast F-2):** всё общение с Claude Code (флаги, stream-json, форматы `~/.claude`) — в одном своём модуле; смена поколения CLI — правка одного модуля.
- **Аудит (roast C-6):** инвариант — журнал команд append-only, действия владельца и агентов различимы; политика retention диалогов сессий — до того, как они станут долговечными (Ф3).
- Раннер — критический компонент: health-check + автоперезапуск + спроектированный переподхват живых сессий при собственном рестарте (roast B-6): идемпотентность по ключу задачи (одна задача — одна живая сессия), состояние `delivered` пишется до/атомарно со spawn.
- Мониторинг лимитов подписки переезжает на сервер.

## 6. План миграции (фазы)

1. **Ф0 (старт немедленно, бюджет 2 недели):** spawn/resume-доставка + три страховки (health-check кредов, heartbeat, pg_dump по крону с одной проверкой restore). Задачи — по обычному процессу в трекере agent-dashboard (AD-19 и далее).
2. **Ф0.5 (параллельно Ф0, архитектурная):** карта заимствований из yao/DSH → ARCHITECTURE.md целевой системы + ADR-серия (модель доставки, модель сессий/журнала, прослойка CLI, схема данных с автором/адресатом, периметр). Материал: docs/03–04 (DSH), docs/06 (yao — готовится), reference/*.
3. **Ф1 (серверный контур):** compose + VPN-периметр + auth, доска задач-UI, матрица секретов, вывод из Supabase, решение по хосту. Ворота: DoD Ф0 достигнут.
4. **Ф2 (паритет):** стриминговый просмотр сессий, wiki-слой документов (С7), PWA поверх VPN. Вывод vault — только после проверенного restore.
5. **Ф3 (канон памяти, C-Н5):** общий стор + двустороннее согласование личных памятей (hooks Claude Code → канон; выгрузка канона в CLAUDE.md/инструкции). Кандидат EverOS оценивается здесь. Retention-политика — до включения долговечности диалогов.
6. Точки риска: двойная запись статусов, пока vault жив (детекторы обязаны работать всё время миграции); доставка кредов на сервер (uid, молчаливый выход CLI); переходный период Ф1 (панель и раннер переезжают — план отката: возврат исполнения на рабочую станцию, описывается в runbook Ф1).

## 7. Критерий выполненности (definition of done)

- Решение задокументировано ADR-ом; ARCHITECTURE.md создан; квартальная задача ревизии границ заведена.
- **Ф0:** команда из панели доходит до агента с состоянием `delivered` (не `sent`), видно в панели; гашение сессии на середине отражается как прерывание, не завершение; рестарт раннера не теряет и не дублирует живые сессии; health-check ловит нечитаемые креды; heartbeat молчит ≤ N минут → уведомление владельцу; restore из pg_dump проверен один раз руками.
- **Ф0.5:** ARCHITECTURE.md + ≥4 ADR целевой системы приняты владельцем.
- **Чек-лист паритета (ворота Ф2, предметы бывших SS):** С1 — статусы всех агентов в реальном времени без терминала; С2 — постановка задачи с телефона (поверх VPN) с подтверждённой доставкой; С3 — вопрос агента → ответ владельца → разблокировка, след в журнале; С4 — задача передана агентом А агенту Б без участия владельца; С5+С7 — документы в каноне: wiki-линки резолвятся, бэклинки видны, русский FTS работает, правка из панели; С6 — всё перечисленное доступно извне через VPN.
- **Ф3:** vault Obsidian выведен; знания и статусы в одном каноне; личные памяти согласуются автоматически; retention-политика действует.
