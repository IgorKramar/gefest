# Decision summary: консолидация оркестрации агентов

- Дата: 2026-08-20
- Фаза: Decide (deep-цикл)
- Входы: discovery (2 раунда), research-дайджест со спайками S1a/S1b/S2, design (4 альтернативы)
- Статус: принято владельцем («Да», 2026-08-20, после разбора «что получаем в каждом случае»); ожидает roast + ADR

## 1. Выбранная альтернатива

**Ступенчатое решение с объявленными воротами** (композиция B-как-основа + тайм-боксированный пилот A):

1. **Немедленно, вне зависимости от исхода пилота:** доставка команд в agent-dashboard переводится на spawn/resume-механику — раннер владеет процессами `claude -p --resume` (stream-json), состояние доставки подтверждаемо. Это лечит боль №2 сегодня и является фундаментом обоих исходов.
2. **Тайм-боксированный пилот yao — 1 неделя** после фикса доставки, на 1–2 реальных задачах, при живом agent-dashboard как страховке.
3. **Выбор по бинарным критериям** (ниже). Правило по умолчанию: **любой стоп-сигнал или прохождение «впритык» = fallback на B** (собственный оркестратор, эволюция agent-dashboard). yao в этом случае остаётся источником идей, как DSH.

Это одно решение, а не отложенное: зафиксированы критерии, срок и исход по умолчанию. «Посмотрим, как пойдёт» исключено конструкцией — неоднозначность трактуется в пользу B.

### Стоп-сигналы пилота (любой = fallback на B)

- **SS-1.** Ассистент без коннектора не проходит валидацию Yao Engine — то есть подписочная авторизация не подключается штатно (спайк S1b проверил образ и код раннера, но не полный контур движка).
- **SS-2.** rc-обновление yao за неделю пилота ломает наш контур (формат, API, песочницы) — темп чужих breaking changes фактически неприемлем.
- **SS-3.** Модель задач yao не выражает «готово = мерж + зелёный пайплайн» и не даёт API для наших детекторов расхождений (API доски не документирован — проверяется руками).
- **SS-4.** Полноценное управление с телефона фактически не работает (Android beta / браузер).
- **SS-5.** Документный слой не покрывает привычки Obsidian (С7: wiki-линки, бэклинки, русский FTS) и нет реалистичного пути покрыть их поверх его API.

### Критерий прохождения

Все SS отсутствуют **и** две реальные задачи прожиты в yao end-to-end (постановка из панели → работа агента со стримингом → мерж → корректный статус), включая хотя бы одну постановку с телефона.

## 2. Почему это решение

- **Спайки открыли обе двери, но не сняли главный риск A.** Подписка работает в контейнере и в yao-образе (S1a/S1b), но контур движка не проверен, а rc-темп (релизы каждые 1–3 дня с рефакторингами ядра) и лицензия («логика верификации», право менять условия) — риски, которые проверяются только прожитой неделей, а не чтением кода. Пилот — самый дешёвый способ превратить их в факты.
- **Пути асимметричны по обратимости.** Миграция с B (своя база + раннер) куда угодно — дёшева; миграция с A — вытаскивание истории из чужих форматов при обвязке, написанной под чужие песочницы. Ошибка в B стоит недели, ошибка в A — месяца. Поэтому при любой неоднозначности исход — B.
- **Spawn/resume-доставка нужна в обоих мирах.** Она чинит самую острую боль (статусы/доставка, ответ владельца №2) немедленно и не выбрасывается ни при каком исходе пилота.
- **Владелец хочет готовую платформу (симпатия к yao заявлена)** — пилот уважает это желание и даёт платформе честный шанс показать 80% из коробки, вместо того чтобы отвергнуть её по бумажным рискам.
- **Страховка уже оплачена:** по решению владельца agent-dashboard живёт до утверждения архитектуры — пилот не создаёт окна, в котором команда без координации.

## 3. Что мы отдаём (принятые минусы)

- Неделя календарного времени на пилот, которая при исходе «B» будет выглядеть потраченной (на деле — купленная определённость + перенесённые уроки, но код пилотной обвязки yao будет выброшен).
- При исходе «A»: постоянный налог на чужой rc-темп, лицензионную привязь (брендинг, верификация), достройку детекторов и памяти поверх недокументированного API — всё из design §2.
- При исходе «B»: 4–7 недель разработки до паритета с yao по C1–C7, bus-factor 1, отказ от «бонусов» платформы (VNC-песочницы, готовые клиенты, интеграции).
- Серую зону подписочного headless на сервере принимаем осознанно (личный контур, свои сессии, свой сервер); эскалация в Anthropic — по желанию владельца, не блокер.

## 4. Границы пересмотра решения

- **DSH дозревает**: появляется durable-интеграция Claude Code (стрим + resume + видимость в UI) и auth в Web UI — пересмотр в пользу DSH-платформы (альтернатива C design-документа), знания уже собраны в этом репо.
- **Anthropic явно запрещает** подписочный headless на сервере (ToS/техблок) — пересмотр бюджетной модели (C-Н1) и, возможно, всей схемы исполнителей.
- **Команда людей растёт** (второй человек-оператор) — пересмотр F7 и, возможно, возврат к вопросу Kubernetes (П-1).
- **Появляется причина для кубера** (второй хост, автоскейл) — деплой-цель меняется с compose (резолюция П-1 это уже предусматривает).
- **Исход «B», но через 3 месяца паритет по С1–С7 не достигнут** — честная ревизия: затянувшийся полуфабрикат хуже платформенного налога.

## 5. Операционные последствия

- Появляется серверный хост (тот же, где AFFiNE, или новый — уточняется при Document): docker-compose, systemd, бэкапы Postgres, периметр (VPN/reverse proxy + auth) — обслуживает владелец.
- `~/.claude/.credentials.json` становится серверным секретом: доставка на хост, права, ротация при логауте; ловушка «CLI молча выходит с кодом 0 при нечитаемых кредах» (найдена в S1b) — обязательная проверка в обвязке.
- Раннер становится критическим компонентом: его падение = агенты не получают команд; нужен health-check и автоперезапуск (образец уже есть: systemd + linger).
- Supabase-облако как хранилище панели пересматривается при переезде на свой сервер (латентность/приватность/бэкапы) — решается в Document/миграции.
- Мониторинг лимитов подписки (rate-limits) переезжает с рабочей станции на сервер.

## 6. План миграции (фазы)

1. **Ф0 (сейчас):** spawn/resume-доставка в agent-dashboard + подтверждаемые статусы доставки. Задачи заводятся по обычному процессу (AD-19+).
2. **Ф1 (параллельно Ф0):** пилот yao — свой образ песочницы (актуальный CLI + креды + hooks), Yao Engine локально, 1–2 реальные задачи, проверка SS-1…SS-5, дневник пилота в этом репо.
3. **Ф2 (по исходу):**
   - **A:** yao на сервер (compose), перенос задач/знаний, достройка детекторов поверх API, вывод vault по мере готовности документного слоя.
   - **B:** серверный контур agent-dashboard (compose + auth + PWA), доска-UI, стриминговый просмотр сессий, wiki-слой документов, вывод vault.
4. **Ф3:** канон памяти (C-Н5): общий стор + согласование личных памятей (hooks Claude Code → канон; выгрузка канона в CLAUDE.md/инструкции). Кандидат EverOS оценивается здесь, не раньше.
5. Точки риска: доставка кредов в контейнеры (uid, молчаливый выход CLI); двойная запись статусов в переходный период (vault ещё жив — детекторы расхождений обязаны работать всё время миграции).

## 7. Критерий выполненности (definition of done)

- Решение задокументировано ADR-ом; ARCHITECTURE.md этого репо создан и отражает выбор.
- Ф0: команда, поставленная из панели, доходит до агента с состоянием `delivered` (не `sent`), и это видно в панели; гашение сессии на середине отражается как прерывание, а не завершение.
- Ф1: дневник пилота содержит вердикт по каждому SS-1…SS-5 с фактами; решение A/B зафиксировано дополнением к ADR.
- Ф2: владелец ставит задачу с телефона и наблюдает работу агента в реальном времени, не открывая терминал.
- Ф3: vault Obsidian выведен из эксплуатации; знания и статусы живут в одном каноне; личные памяти согласуются автоматически.
