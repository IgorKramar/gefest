# Design: модель сессий и журнала (D-5)

- Дата: 2026-08-21 · Масштаб: light · Вход: discovery + ответы владельца (Q1 — вехи с drill-down в диалог; Q2 — вехи на tool-вызовы; Q3 — саммари при завершении/усыплении)

## Общая часть (не зависит от развилки)

- **Машина состояний сессии** (консолидация ADR-0006/0007, одно перечисление): `spawning` → `running` ⇄ `waiting_answer` (+ за флагом: `stopping` → `sleeping_cold`) → терминальные `completed` | `interrupted` | `failed`; переводит только раннер, каждый переход = событие session_events; осиротевшие `running`/`spawning` при старте бинаря → `interrupted` событием reconciliation (ADR-0005).
- **Родословная:** ретрай/рестарт → новая сессия с `parent_session_id`; у задачи живая — максимум одна (частичный UNIQUE, ADR-0005); панель показывает цепочку.
- **Таксономия вех (Q2-б):** границы ходов; tool-вызов (имя, длительность, статус — **без аргументов**); вопрос агента; interrupted; limit-события (белый список ADR-0007); `raw_state`/ENOSPC. Маркеры доставки — в `command_deliveries`, в вехах их нет (ADR-0007).
- **Саммари (Q3-а):** исполнитель суммаризирует при завершении и при уходе в `waiting_answer`; невыполнение контракта (умер без саммари) → веха `summary_missing`, панель показывает последнее старое с пометкой; ретрай-путь не блокируется.
- **Инвариант «видимое = залогировано»:** статусы, лента и хронология панели — только из БД. Drill-down в диалог — явное действие «показать сырьё» (см. развилку), не источник статуса.

## Развилка: где живёт диалог для drill-down

**A. Вехи-указатели в сырьё.** Веха границы хода несёт `(raw_file, byte_from, byte_to)`; API Гефеста по вехе отдаёт срез raw-файла (читает раннер, доступ по RLS-правам задачи); панель рендерит диалог хода. После janitor 30 дней — «сырьё истекло», остаются вехи и саммари.

**B. Диалог-события в БД.** Тексты user/assistant-сообщений (без tool-аргументов) дублируются событиями session_events под scope_class; drill-down живёт 90 дней и попадает в бэкап; сырьё остаётся для форензики.

| Критерий | A: указатели | B: диалог в БД |
|---|---|---|
| Поза ADR-0005 («сырьё вне БД», C-С1) | Соблюдена | Нарушена: клиентские тексты в БД и бэкапе |
| Глубина drill-down | 30 дней (сырьё), дальше саммари | 90 дней |
| Приватность/retention | Один носитель текста (raw), одна политика | Второй носитель текста — вторая политика удаления |
| Объём БД | Вехи лёгкие | Растёт с болтливостью модели |
| Реализация | Смещения при записи вех (writer уже стримит) + endpoint среза | Парсинг+запись каждого текст-события |
| Устойчивость к битому raw | Срез 404 → саммари | Диалог выживает |

**Lean автора — A**: диалог глубже 30 дней нужен редко (есть саммари и вехи); ключевые тексты и так в БД по построению — команды владельца (commands, ADR-0007) и вопросы агента (session_events); B заводит второй носитель клиентского текста со своей политикой «удалить с производными» — ровно та расползающаяся поверхность, которую ADR-0005 закрывал. Если 30 дней окажется мало — retention сырья это настройка janitor, не смена модели.

Не рассматривалось: live-хвост сырья в панель (Q1 снял), полный ES (ADR-0005 отверг), тексты в вехах-указателях частично (гибрид = обе политики сразу, худшее обоих).
