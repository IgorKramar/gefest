# Decision summary: схема данных Гефеста (D-2)

- Дата: 2026-08-20 · Фаза: Decide (deep) · Входы: discovery (2 раунда, C-Д1…C-Д4), research (донор DDL + веб-паттерны), design (A/B/C/D)
- Легенда: см. discovery; плюс `A/B/C/D` — альтернативы design; «донор» — agent-dashboard.
- Статус: **принято владельцем** («Согласен с А + тогда стоит ещё будет сделать mcp для агентов, чтобы им было легко ходить к API Гефеста», 2026-08-20). Ожидает roast + ADR-0005.

## 1. Выбранная альтернатива

**A: «журнал + материализованное состояние»** — по design §2 целиком (эскиз ~30 таблиц там — нормативный вход ADR-0005):

1. Каждая машина состояний = append-only поток `(stream_id, version)` UNIQUE + state-таблица; **обе пишутся одной транзакцией приложением**; триггеры — только инварианты (запрет UPDATE/DELETE журналов; защита порядка `updated_at <= NEW.ts` где применимо).
2. Commands: две оси = две структуры (`execution_state` в commands + append-only `command_deliveries`); идемпотентность — частичными UNIQUE («одна живая команда старта / одна running-сессия на задачу»); виды команд — **перечисление, не строка** (RCE-защита донора).
3. Сессии (C-Д1): вехи (`session_events`) + саммари (пишет исполнитель в конце сессии) в БД; сырой stream-json — файлами с ротацией; один писатель на стрим (раннер) — лечит commit out-of-order.
4. Канон памяти — DDL по ADR-0003 (классы/скоупы/слои, кандидаты с копией сырья, embeddings-дверь, recall_log метаданными).
5. RLS с v1 (C-Д2): `set_config('app.actor_id', $1, true)` в транзакции; `FORCE ROW LEVEL SECURITY`; роли `gefest_app`/`gefest_owner` — не владельцы таблиц; `gefest_migrator` — владелец, только миграции; политики через `(SELECT current_setting(...))`; SECURITY DEFINER — с `SET search_path = ''`.
6. Идентификаторы: bigserial PK внутри + бизнес-ключи UNIQUE (Atlassian-ключи задач `GENERATED` от per-project счётчика) + UUIDv7 приложением для внешних id.
7. FTS: хранимый `tsvector GENERATED` с весами A/B, конфигурация `russian` (стеммит и английские токены); pg_trgm — дополнение. Проверка на своём корпусе (`ts_debug`) — в первой миграционной задаче.
8. Журналы: BRIN + batched-DELETE retention; ключ будущего партиционирования — в PK заранее. SSE: NOTIFY-будильник (пустой payload) + поллинг с курсором (`consumer_offsets`); после reconnect PgListener — обязательный re-read.
9. Миграции: штатный `sqlx migrate`, embedded, forward-only, чек-суммы.
10. **Граница доступа + MCP (дополнение владельца):** агенты не имеют прямых подключений к БД; парадный вход — **MCP-сервер Гефеста** (rmcp, тот же бинарь): recall памяти (ADR-0003), журнал (вопрос/блокировка/закрытие), статусы задач (событиями), отчёт о ходе; плюс CLI-обёртка для скриптов. Состав и авторизация инструментов — отдельное решение **D-16** (заведено в decision-map), поверхность проектируется вместе с D-4/D-9.

Под-параметры (предложения исполнителя, приняты по умолчанию с согласием на A; корректируемы до ADR):
- (а) **Аудит-триггер на прямые правки state-таблиц** мимо приложения (ловит «руками поправил в psql») — да.
- (б) **Retention:** вехи session_events — 90 дней; сырьё-файлы — 30 дней; саммари — вечно; recall_log — 6 мес (ADR-0003).
- (в) **Стартовые command_kinds:** start | stop | answer | note | assign.

## 2. Почему

Читаемое состояние + полная история без eventual consistency (в. 2 владельца — гибрид); все инварианты §3 discovery закрыты конструкциями, не дисциплиной; исправлены 16 костылей донора при сохранении его 10 паттернов; RLS-каркас един для второго оператора и скоупов памяти; C-С1 — сырьё вне БД; research-консенсус «журнал+state для малых систем» — прямое попадание.

## 3. Что отдаём

Дисциплина «каждый переход — через событие» держится на том, что писатель один (бинарь) — второй процесс-писатель запрещён архитектурно (ADR-0001/D-3); строгость RLS с v1 — плата в отладке; ~30 таблиц и 1.5–2 недели схемной работы до первого кода GF-2; полный ES отвергнут — если когда-то захочется replay *всех* доменов, будет доступен только для сессий/памяти/задач (их потоки полны).

## 4. Границы пересмотра

Второй процесс-писатель становится нужен (масштаб/отказоустойчивость) → пересмотр транзакционной дисциплины (outbox/логическая репликация); retention-DELETE заболел (десятки ГБ) → декларативное партиционирование (ключ в PK уже есть); FTS-проверка на корпусе проваливается → конфигурация russian+simple / trgm-усиление; D-15 (Jira-модель) потребует колонок сверх дверей → обычные forward-миграции.

## 5. Операционные последствия

ADR-0005 фиксирует эскиз design §2 как нормативный; первые миграции — задача GF-5 (после ADR); смоук-тесты обязательные: RLS с пулом (утечка set_config), PgListener reconnect, `ts_debug` корпуса; данные донора: канон памяти мигрируется по плану ADR-0003 (Ф2), оперативные задачи/журнал AD — скриптом при cutover Ф2 (двойной учёт до cutover — по правилу «vault/AD — истина до дня переключения»).

## 6. Критерий выполненности

ADR-0005 принят; D-16 в карте; миграции 0001..000N применяются на чистую БД и проходят смоук-тесты; инварианты проверены отрицательными тестами (UPDATE журнала — отказ; вторая живая команда старта — отказ; RLS: чужой скоуп невидим; событие с прошлым ts не откатывает состояние); Rust-enum'ы синхронизированы с lookup-таблицами (`sqlx::Type`).
