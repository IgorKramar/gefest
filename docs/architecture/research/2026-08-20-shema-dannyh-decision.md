## 1. Выбранная альтернатива

**A: «журнал + материализованное состояние»** — design §2 как основа, со следующими **поправками эскиза (ред. 2, из roast)**:

1. **Конкурентность (CC-1):** каждый переход состояния — `INSERT event (version = revision+1)` + `UPDATE state ... WHERE id=$1 AND revision=$n` в одной транзакции; неуспех CAS → перечитать и повторить (retry-протокол в прослойке доступа, один на все домены). Триггер порядка — защита второй линии, не первой.
2. **Lease и восстановление (CC-1):** `commands.taken_at` + правило lease: `taken` старше T (5 мин) — доступна повторному захвату (`WHERE execution_state='taken' AND taken_at < now()-T`); **reconciliation при старте бинаря**: running/starting-сессии без живого процесса → `interrupted` событием, `version` восстанавливается сканом хвоста стрима (не MAX доверчиво); осиротевшие процессы находятся по метке процесса (`--name`-паттерн yao). Легальная починка — команда `hef task fix-state` (корректирующее событие), прямые UPDATE запрещены и аудируются.
3. **Канал панели (CC-2):** поллер не продвигает курсор через разрыв id: обнаружив пропуск, ждёт до 5 с его коммита; не дождался — фиксирует `gap`-запись в лог поллера и продвигается. Разрывы наблюдаемы, не молчаливы.
4. **Ключи задач (CC-3):** присвоение **функцией при INSERT**: `SELECT next_seq FROM project_counters WHERE project_id=$1 FOR UPDATE` → `key = project_key || '-' || seq` (stored, UNIQUE). НЕ GENERATED. `projects.key` **иммутабелен** (переименование проекта меняет `title`, не key); `pools.kind` → lookup-таблица.
5. **Trust-класс (CC-4):** `task_events.origin CHECK (owner | agent | agent_external)` — `agent_external` для действий, инициированных недоверенным контентом (заполняется исполнителем/раннером по эвристике источника; дверь для D-16). **Интерим до D-16:** MCP-запись — только события своей сессии (actor из контекста процесса раннера, не из параметров вызова); `assign` — только владельцу; запись в память — только через memory_candidates.
6. **ФС-контур сырья (CC-5, подтверждено владельцем):** каталог сырья — владелец ФС только раннер (0700); **в бэкап не входит** (принято: сырьё — отладочный материал, RPO = потеря при смерти диска; саммари+вехи в БД покрыты pg_dump); janitor-таск бинаря (tokio, ежесуточно) — ротация 30 дней; при ENOSPC — сессия продолжает работу без записи сырья, событие `raw_write_failed` в стрим; метрика диска в панель; `sessions.raw_state CHECK (present | rotated | failed)`; «удалить с производными» (ADR-0003) включает raw-файл.
7. **Приватность сессий (CC-6):** фильтр ADR-0003 распространяется на `sessions.summary` и `session_events` по `project.scope_class` — тот же fail-loud конфиг: клиентские сессии не попадают ни в одну фоновую LLM-задачу.
8. **RLS и аудит (CC-7):** RLS-перечень расширен: memory_*, sessions/session_events, journal, commands, **observations, tasks** — политики видимости по скоупу проекта (сегодня «все свои» — политика одна, но каркас полный); таблица **`audit_log`** в эскизе (append-only со своими запретами, retention 12 мес, храним факт+кто+когда+таблица+PK, без old/new — не плодим копий данных); срабатывание — **алерт**, не лог (CC-9); psqlrc-хелпер `SELECT gefest_login('owner')` + тест «NULL-контекст → пусто»; границы признаны: аудит ловит честные ошибки, не злонамеренного владельца со set_config (принято).
9. **Фазировка (CC-8, подтверждено владельцем):** **v1-ядро — 14 таблиц** (actors, roles_profile, projects, project_counters, tasks, task_events, task_statuses, commands, command_kinds, command_deliveries, sessions, session_events, journal, consumer_offsets) + audit_log; RLS-политики — на ядро. Волна 2 (forward-миграции, «двери, не активны» — маркер в комментарии DDL, ревизия RLS при активации): memory_* (по плану Ф2 ADR-0003), boards/board_columns/pools/pool_tasks, tags/task_tags/task_dependencies, observations, exports_log.
10. **Деплой миграций (CC-8):** отдельный шаг `hef migrate` в compose (тот же бинарь, DSN `gefest_migrator` только на этом шаге; app-сервис стартует после успешного migrate); bootstrap-скрипт создаёт три роли (пароли — из env/secrets, не в миграциях); **откат = restore pg_dump (RPO ≤ 24 ч)** — принято словами.
11. **Правила надолго (CC-9):** cutover-импорт данных AD — только через события `imported` API бинаря, не прямой SQL; **истина перечислений — Rust-enum**, lookup — зеркало, наполняется только миграциями, runtime-INSERT запрещён; значения execution_state / исходов доставки / состояний сессий — **предварительные: D-4/D-5 правят их forward-миграцией без пересмотра ADR-0005**; контракт саммари (минимум: принятые решения, изменённые файлы, причины отказов/блокировок — то, при чём вехи не жалко терять) — проверяется хуком конца сессии; счётчик удалённого retention-ом — в панель; семантика MCP-инструментов не срастается с транспортом MCP; специфика PG17 не используется (PG18-путь свободен).
12. Остальное — по design §2 и ред. 1: сессии с саммари исполнителя, UUIDv7 приложением, FTS с весами, BRIN+retention, NOTIFY-будильник, sqlx migrate embedded, MCP — парадный вход (D-16).

Календарная честность (H-1): v1-ядро — ~30–40 инженер-часов; при темпе владельца — 3–5 недель календаря; полный эскиз довозится волной 2 без пересмотра решений.

## 2. Почему

(Без изменений от ред. 1: гибрид по консенсусу research; инварианты конструкциями; 10 паттернов донора сохранены, 16 костылей исправлены; RLS-каркас на второго оператора; C-С1 — сырьё вне БД.) Ред. 2 добавляет: все 39 находок roast закрыты конструкциями или явными принятиями — ни одна не оставлена «на дисциплину».

## 3. Что отдаём

Ред. 1 + явные принятия ред. 2: сырьё сессий не бэкапится (RPO — смерть диска); аудит не защищает от осведомлённого владельца; «потоки сессий полны **в пределах retention**» — replay старше 90 дней невозможен, компенсация — контракт саммари; интерим-MCP урезан до D-16; полный эскиз доезжает волной 2 (панель бордов и память ждут её).

## 4. Границы пересмотра

Ред. 1 (второй писатель; retention заболел; FTS-корпус; D-15) + новые: lease-таймаут T и gap-таймаут 5 с — параметры, правятся конфигом по факту; счётчик gap-записей поллера растёт → пересмотр канала (xmin-курсор/логическая репликация); audit_log-алерты чаще раза в месяц → ревизия причин (руки лезут в psql — чинить инструмент, не человека).

## 5. Операционные последствия

GF-5 (заводится этим решением): миграции v1-ядра + смоук-тесты, **описанные сценарием и признаком провала**: (1) RLS-пул: два запроса через один pooled-коннект от разных actor_id — второй видит чужие строки = провал; (2) PgListener: kill соединения listener → события за окно реконнекта доезжают поллером, счётчик gap > 0 = наблюдаемо, потеря без gap-записи = провал; (3) FTS: `ts_debug('russian', <корпус из 20 реальных заголовков/тел>)` — русские словоформы стеммятся, английские термины находятся, иначе — конфигурация пересматривается. Отрицательные тесты: UPDATE журнала — отказ; вторая живая команда старта — отказ; событие с прошлым ts — не откатывает; NULL-RLS-контекст — пусто; runtime-INSERT в lookup — отказ (грант/триггер).

## 6. Migration path

1. GF-5: bootstrap ролей + миграции v1-ядра + смоук/отрицательные тесты (первый Rust-код — прослойка доступа с CAS-retry).
2. GF-2/GF-3 (раннер + страховки) — поверх ядра.
3. Волна 2 схемы — forward-миграции по мере фаз (память — Ф2 ADR-0003; борды — к панели; observations — к детекторам).
4. Cutover Ф2: данные AD → события `imported` через API; день переключения = заморозка vault/AD на запись (правило ADR-0003 п.7, распространённое ред. 1 этого решения на AD); сверка контента до вывода.

## 7. Критерий выполненности

ADR-0005 принят; GF-5 заведена и исполнена (миграции применяются на чистую БД, все смоук/отрицательные тесты зелёные); Rust-enum ↔ lookup синхронизированы CI-тестом; reconciliation при старте проверен убийством раннера с живой сессией; gap-лог поллера наблюдаем в панели (волна 2 — до тех пор в логах бинаря).
