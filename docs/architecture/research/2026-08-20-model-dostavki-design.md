# Design: модель доставки (D-4) — альтернативы

- Дата: 2026-08-20 · Фаза: Design (deep) · Входы: discovery (2 раунда, C-Д1а…Д6а + спайк S3), research (S4, SIGTERM, лимиты, доноры)

## 1. Проблема и силы

Гарантированная доставка указаний исполнителям: старт, указание живому (граница шага — C-Д1а), ответ на блокирующий вопрос (сон с остановкой контейнера — C-Д4а), stop, лимиты с ручным слотом и приоритетами (C-Д2а), квоты 5+1/2 (C-Д3а), 3 ретрая → инцидент (C-Д5а), единый инбокс для D-9 (C-Д6а). Силы: F-Д2 (подтверждение — от кого), F-Д4 (каждая гарантия — код раннера), «sent ≠ delivered» как символ веры проекта.

**Общее для всех альтернатив (закрыто research-ом):** транспорт — stdin живого процесса (S3/S4) + SIGTERM для stop; истина — таблицы ADR-0005 (commands, deliveries, inbox-очередь per-исполнитель); лимиты — `system/api_retry` + пауза очереди до `resets_at` (ручной слот вне паузы); квоты и приоритеты — планировщик раннера поверх таблиц.

---

## 2. Альтернатива A — push раннером + delivered-по-потоку

**Одной строкой:** раннер пишет указание в stdin (в любой момент — S4 гарантирует границу шага); `sent` = записано в stdin живого процесса; **`delivered` = после записи поток сессии продолжился** (следующее событие stream-json от процесса) — наблюдаемый факт без участия модели.

- **Силам:** F-Д2 — подтверждение честное, но косвенное: «процесс жив и работает после вручения» (не «модель осознала»); F-Д4 — минимум кода (запись + наблюдение уже имеющегося потока); C-Д4а — ответ спящему: resume контейнера → stdin → продолжение потока = delivered.
- **Легче:** ноль требований к поведению модели; работает для всех видов указаний одинаково. **Тяжелее:** формально «доставлено процессу», не «принято агентом»; крайний случай — сообщение легло в очередь stdin, процесс умер до границы шага: раннер увидит отсутствие продолжения → перекладывает в недоставленные при reconciliation (закрываемо).

## 3. Альтернатива B — pull исполнителем через MCP

**Одной строкой:** раннер ничего не пишет в stdin; исполнителю в системный промпт — «на границах шагов проверяй инбокс инструментом»; `delivered` = агент вызвал `inbox_ack`.

- **Силам:** F-Д2 — сильнейшее подтверждение (модель явно приняла); но F-Д4 наоборот: гарантия держится на **дисциплине модели** («проверяй» забывается — весь проект построен на недоверии к этому); сон до ответа не работает без пуша (спящий не поллит); каждый поллинг — токены (C-Н1).
- **Легче:** не зависит от недокументированной stdin-семантики (но она уже проверена спайками — аргумент испарился). **Тяжелее:** везде.

## 4. Альтернатива C — push + явный ack инструментом (гибрид)

**Одной строкой:** как A, но после вручения модель обязана вызвать MCP `ack(указание)` — `delivered` только по ack.

- **Силам:** F-Д2 — максимальная гарантия «модель осознала»; цена — системный промпт обязывает, модель может забыть (ложные undelivered при фактическом исполнении), +1 tool-вызов токенов на каждое указание; F-Д4 — раннер ведёт таймеры ack.
- **Ниша:** не как общий режим, а как **опция для критичных указаний** (стоп-класс исключён — он SIGTERM; кандидат — ответы на блокирующие вопросы, но там delivered и так наблюдается через resume+продолжение).

## 5. Альтернатива D — статус-кво AD (сигнал в сокет живой сессии)

Отклоняется по построению: `sent` без канала подтверждения — это боль №2, ради которой существует Гефест. База сравнения.

---

## 6. Матрица

| Сила | A: push+поток | B: pull+ack | C: push+ack | D: сокет |
|---|---|---|---|---|
| Честность delivered (F-Д2) | good (наблюдаемо, косвенно) | **good** (явно) | **good** (явно) | poor |
| Независимость от дисциплины модели | **good** | poor | fair | good |
| Токены/лимиты (C-Н1) | **good** (ноль) | poor (поллинг) | fair (+1 вызов) | good |
| Сон до ответа (C-Д4а) | **good** | poor | fair | poor |
| Толщина раннера (F-Д4) | **good** | fair | fair | good |
| Единый инбокс для D-9 (C-Д6а) | good | fair | good | poor |

## 7. Что сознательно НЕ рассматривали

Interrupt-control через stdin (не документирован — только SIGTERM); exactly-once (недостижимо — at-least-once + идемпотентность ADR-0005); отдельный message-broker (NATS/Redis — новый сервис против F7, истина уже в Postgres); долгий поллинг агентом файлов/ФС (канал мимо Гефеста — запрещено C-И2).

## 8. Что нужно узнать, чтобы решить

Ничего внешнего: спайки закрыли механику. Рекомендация design: **A** как общий режим + **C-дверь** (поле `requires_ack` у указания, выключено по умолчанию) на случай, если практика покажет классы сообщений, где косвенного подтверждения мало. B отклоняется целиком (дисциплина модели — то, чему проект не доверяет по конституции).
