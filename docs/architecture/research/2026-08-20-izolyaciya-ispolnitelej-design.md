# Design: модель изоляции исполнителей (D-3) — альтернативы

- Дата: 2026-08-20 · Входы: discovery (2 раунда, C-И1…C-И5, П-И1), research (контейнеры/bwrap/эфемерные БД/housekeeping)

## 1. Проблема и силы

Per-task эфемерная песочница исполнителя с жёсткой изоляцией (C-И1/И2), лимитами с v1 (C-И3), dev-БД и комплектом ресурсов от Гефеста-брокера (C-И4/И5), без висящих остатков, с понятным путём в поды при появлении причины (П-И1). Силы: изоляция против простоты (F-И1), скорость старта (F-И3), лёгкий класс против зрелой обвязки (F-И4).

**Общее для всех альтернатив (из ответов и research):** эфемерная dev-БД — общий Postgres + template-клон (~10–40 мс) из раннера, сериализованно, `DROP ... WITH (FORCE)` при уборке; prepare-комплект (worktree, `~/.claude`-набор: креды ro + сгенерированная память роли + hooks, scoped-токены, env) собирает раннер идемпотентно (маркер-хэш конфига — yao); housekeeping — labels/registry + reaper + TTL-sweep; кандидаты памяти копируются при предложении.

---

## 2. Альтернатива A — rootless-контейнер на задачу (podman/docker + bollard)

**Одной строкой:** раннер через bollard создаёт per-task контейнер (образ: Node + Claude Code CLI + git), всё в одном механизме: ФС/сеть/pid-namespaces, cgroups-лимиты, labels для reaper.

- **Силам:** изоляция «жёстко» — namespaces целиком, том задачи — единственная видимая ФС; лимиты — `--memory/--cpus` нативно (проверить systemd-делегирование cpu/cpuset!); сеть — pasta + правила «Anthropic, git-хостинги, MCP Гефеста» (сетевой фильтр — на уровне прокси/файрвола, контейнер даёт каркас); housekeeping — Ryuk-паттерн дословно; **путь в поды — дословный** (контейнер = под).
- **Легче:** один зрелый механизм на всё; восстановление реестра из labels переживает crash раннера. **Тяжелее:** образ (~200+ МБ с Node/CLI) — собирать и обновлять вслед за CLI-релизами; сокет рантайма у раннера — root-эквивалент (rootless смягчает); cold-start ловушки (`--userns auto` прогрев).
- **Усилия:** ~1 неделя (образ + bollard-обвязка + reaper + прогрев). **Ломается:** если старт контейнера окажется заметным в UX (сотни мс — приемлемо; секунды на холодном — прогревать).

## 3. Альтернатива B — bwrap-песочница + systemd-scope + прокси (путь вендоров)

**Одной строкой:** как Claude Code `/sandbox` и Codex: bwrap (ФС-allowlist, `--unshare-net`) + socat/HTTP-прокси с allowlist доменов + `systemd-run --user --scope` для CPU/RAM-лимитов.

- **Силам:** старты мгновенные, нулевой контейнерный мусор (PDEATHSIG), нет образа — CLI хоста; изоляция ФС — allowlist (правильная модель), сеть — только через наш прокси (бонус: фильтрация доменов из коробки — сильнее контейнерного «всё наружу»).
- **Легче:** минимум движущихся частей в рантайме (F7), обновление CLI — обычный апдейт хоста. **Тяжелее:** собираем сами из трёх частей (bwrap + scope + прокси-компонент с allowlist — его писать и нянчить); известные обходы (denylist через `/proc/self/root` — только allowlist-дисциплина); путь в поды — переписывание слоя; лимиты и изоляция — два разных механизма (двойная отладка).
- **Усилия:** ~1 неделя (враппер + прокси + scope-обвязка), но прокси — новый постоянный компонент. **Ломается:** если понадобится образ-версионирование окружений задач (у контейнеров бесплатно) или сетевые политики сложнее allowlist доменов.

## 4. Альтернатива C — статус-кво: голые процессы + Unix-права

Процессы под отдельными uid per-task, chmod-дисциплина. **Отклоняется по построению:** «жёстко» (C-И2) невыполнимо — общий netns, общий /tmp, /proc всех видно; лимиты — только через те же systemd-scope (полпути к B); roast-находка C-1 (чужое сырьё) остаётся. Включена как база сравнения.

## 5. Матрица

| Сила | A: контейнер/задачу | B: bwrap+scope+прокси | C: процессы+uid |
|---|---|---|---|
| «Жёстко» (C-И2) | **good** | good (allowlist-ФС + no-net) | poor |
| Лимиты v1 (C-И3) | **good** (нативно) | fair (второй механизм) | fair |
| Простота/F7 | fair (образ, сокет, прогрев) | fair (3 самодельные части, свой прокси) | **good** |
| Скорость старта | fair (сотни мс, прогрев) | **good** (мгновенно) | good |
| Housekeeping | **good** (labels+reaper, переживает crash) | good (PDEATHSIG) | fair |
| Путь в поды (П-И1) | **good** (дословно) | poor (переписывание) | poor |
| Сетевая фильтрация доменов | fair (строить отдельно) | **good** (прокси в конструкции) | poor |

## 6. Что сознательно НЕ рассматривали

MicroVM (Firecracker/Kata) — изоляция сверх угроз модели, операционный класс не наш (F7); Kubernetes сейчас — П-1/П-И1; DinD — снят ответом №5; общий контейнер на всех — не изоляция; VM на клиента — «один клиент = том» достигается томами и в A.

## 7. Что нужно узнать, чтобы решить

Ничего внешнего. Развилка — по весам: **A** побеждает по «жёстко + лимиты + housekeeping + путь в поды» (четыре силы), **B** — по «скорость + фильтрация доменов» (две). Рекомендация design: **A (rootless-контейнер на задачу)** с двумя заимствованиями из B: (1) прокси-фильтрация доменов добавляется в A на уровне egress контейнерной сети (когда дойдут руки — D-7); (2) если cold-start окажется болью — bwrap-режим для «лёгких» задач как оптимизация позже (двери не закрываются). Runtime: podman rootless предпочтителен; docker rootless допустим, если на хосте окажется проще — механика bollard идентична (решение при GF-2, не ADR).
