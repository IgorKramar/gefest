# Discovery: организация монорепы (D-17), раунд 1

- Дата: 2026-08-21 · Масштаб: deep (флаг владельца; обоснование: раскладка каменеет — пути врастают в CI/sqlx/Docker/импорты; первое решение области «организация кода») · Вход: запрос владельца 2026-08-21

## Problem

Репозиторий `gefest` сегодня — docs-only (+`reference/` в gitignore). Перед первым кодом (GF-5/GF-2) решить: раскладка Rust-крейтов и фронта, workspace-структура, границы модулей, где живут миграции/скрипты/образы/CI-артефакты, чем управляется многоязыковая сборка.

## Forces

- Один бинарь в проде (ADR-0004: axum-панель + раннер + MCP в одном процессе; C-С1) — но кодовых единиц больше: фальшивый исполнитель (отдельный бинарь для тестов, ADR-0007), CLI `hef`, будущие контрактные тесты S3–S5 (ADR-0009).
- Фронт: React 19 + Vite 8 + TS, Bun — toolchain (ADR-0004); статика раздаётся axum-ом.
- Миграции sqlx — embedded в бинарь (ADR-0005), offline-метаданные (`sqlx prepare`) коммитятся (ADR-0012).
- CI режет job-ы по путям (ADR-0012) — раскладка обязана давать чистые path-фильтры.
- Два Docker-образа: сам Гефест (compose) и образ исполнителя (Node+CLI, конвейер обновления вслед релизам CLI — ADR-0006).
- Один разработчик + агенты-коммиттеры: границы модулей должны быть очевидны агенту без чтения всей истории.
- docs/ — устоявшаяся структура (ADR, research, tasks, диаграммы) — не ломать.
- Rust-паттерны: у бинаря есть искушение остаться одним крейтом (быстрые сборки простоты) против workspace (границы, независимые тесты, кэш).

## Existing constraints

Repo: GitHub IgorKramar/gefest, main защищённый (ADR-0012); reference/ — gitignored клоны доноров; никакого кода пока нет — чистый лист.

## Open questions (владельцу, раунд 1)

- **Q1. Гранулярность Rust-workspace:** (а) workspace из нескольких крейтов по границам доменов (например: `core` — типы/перечисления-истина, `db` — прослойка доступа ADR-0005, `runner` — супервизор+прослойка CLI, `api` — axum owner+MCP, `hef` — главный бинарь-сборка, `fake-executor` — тестовый бинарь); (б) один крейт с модулями + отдельный крейт только для fake-executor — проще, но границы держатся дисциплиной. Что ближе?
- **Q2. CLI `hef`:** подкоманды главного бинаря (`hef serve`, `hef migrate` — один артефакт деплоя) — или отдельный клиентский бинарь, говорящий с API? Напомню: `hef migrate` уже назван отдельным compose-шагом с DSN мигратора (ADR-0005).
- **Q3. Статика фронта:** (а) embed в Rust-бинарь (rust-embed: один артефакт, деплой = один файл); (б) каталог рядом, axum раздаёт с диска (пересборка фронта без пересборки Rust). Что важнее — атомарность деплоя или независимость пересборок?
- **Q4. Верхний уровень:** (а) `crates/*` + `web/` + `docs/` + `infra/` (Dockerfile-ы, compose, deploy.sh, headscale-конфиги GF-6); (б) `apps/*` + `packages/*` (JS-мир) — для одного фронта и Rust-ядра выглядит чужим. Возражения против (а)?
- **Q5. Оркестратор задач сборки:** justfile (рецепты `just dev`, `just check`, `just migrate`) поверх cargo/bun — или mise tasks (mise уже твой тулчейн-менеджер), или голые cargo/bun в README? Turborepo/nx не предлагаю — один фронт.
- **Q6. Контрактные тесты S3–S5 и фальшивый исполнитель:** живут в крейте fake-executor рядом с тестами интеграции — или отдельная верхнеуровневая папка `tests/contract`? (Влияет на path-фильтры CI: contract-тесты гоняются при изменении раннера/прослойки.)
- **Q7. Образ исполнителя:** его Dockerfile и конвейер обновления (пин CLI, ADR-0009) — в `infra/executor-image/` этого же репо, или отдельный репозиторий (свой цикл релизов вслед CLI)? Рекомендация — этот же репо: один PR меняет пин CLI и контрактные тесты вместе.

## Ответы владельца (раунд 1, 2026-08-21)

- Q1: (а) — workspace из нескольких крейтов по доменам.
- Q2: по рекомендации архитектора — **подкоманды главного бинаря** (`hef serve`, `hef migrate`; клиентские `hef remote …` — будущая группа, дверь).
- Q3: (а) — embed статики в бинарь: «атомарность деплоя, бэк и фронт связаны непосредственно».
- Q4: (а) — `crates/*` + `web/` + `docs/` + `infra/`.
- Q5: just («достаточно зрелый» — подтверждено архитектором; nx/turborepo отклонены: ценность — кэш графа JS-пакетов, у нас один фронт, Rust кэширует cargo).
- Q6: контрактные тесты — верхнеуровневые `tests/contract` (интеграционные).
- Q7: образ исполнителя — в этом же репо (`infra/executor-image/`), один PR меняет пин CLI и контрактные тесты вместе.

## Success criteria

Агент-коммиттер по имени каталога понимает, куда класть код; CI-фильтры не пересекаются ложно; `sqlx prepare`, embed миграций и фронт-сборка работают в workspace без обходов; деплой остаётся «compose up» с понятными артефактами; раскладка переживает волну 2 схемы и GF-7 без переезда.
