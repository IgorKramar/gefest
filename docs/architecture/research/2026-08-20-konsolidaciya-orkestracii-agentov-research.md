# Research-дайджест: консолидация оркестрации агентов

- Дата: 2026-08-20
- Фаза: Research (deep-цикл), после discovery раунда 2
- Метод: 4 параллельных исследования — (1) официальная документация Claude Code/Anthropic, (2) веб-разведка экосистемы DSH, (3) разбор исходников DSH (`reference/deepseek-harness`), (4) веб-разведка yao (код + доки из GitHub)

## R1. Claude Code как управляемый исполнитель — техника готова, юрисдикция серая

- Headless: `claude -p`, `--output-format stream-json` (+ partial messages), `--resume <session-id>` / `--continue`, `--permission-mode`, `--allowedTools`, хуки в `-p` — всё поддержано официально.
- **Подписка Max на сервере**: OAuth-токен (`~/.claude/.credentials.json` / `CLAUDE_CODE_OAUTH_TOKEN`) в headless **технически работает**, но официальная позиция: сторонним продуктам нельзя предлагать claude.ai-логин без одобрения; **Agent SDK принимает только `ANTHROPIC_API_KEY`** (подписку не читает, by design). Managed Agents — тоже только API-ключ.
- Наша трактовка риска (не юрзаключение): владелец подписки, запускающий свои же CLI-сессии на своём сервере — ближе к обычному использованию (ssh+tmux), чем к «стороннему продукту с claude.ai-логином». Оркестрация своей панелью — серая зона; эскалация — письмо в Anthropic. Чисто SDK-путь = API-ключ = нарушение C-Н1 (бюджет).
- Параллельные сессии: лимиты не документированы числом; остаток виден в `~/.claude/rate-limits.json` (у нас уже используется панелью).

## R2. DSH: экосистема и стабильность

- rc.7 (17.08) → rc.8 (19.08): **несовместимый формат хранилища между rc**; роадмапа к stable нет; README обещает ломать совместимость.
- **Удалённый доступ официально запрещён по дизайну**: bind 127.0.0.1, `--host 0.0.0.0` отклоняется CLI («would expose RCE»), auth не построен. Путь наружу — SSH-туннель/VPN или свой reverse proxy + `--trusted-host`; конфиг-плоскость (настройки/креды/пресеты) остаётся loopback-only даже через прокси.
- Community-плагины удалёнки/мобильности (dsh-pocket, dsh-web-ui remote, deepseek-harness-auth) — моложе недели, ни одного независимого подтверждения «работает в бою».
- rc.7/rc.8 добавили интеграцию Claude Code/Codex **в ядро** (Profile Bundles, задачи в Job Panel) — часть плагинов устареет.
- dsh-crew работает в обратную сторону (Claude Code — хост, DSH — воркеры). dsh-agent-teams (631⭐) — самый добросовестный командный плагин, но сам документирует «модель может завершить работу, не обновив статус задачи».

## R3. DSH: исходники (решающие факты)

- **`subagent-claude-code` — one-shot fire-and-forget**: текст → один финальный текст. Стрим Claude Code (tool-calls, рассуждения) сознательно выбрасывается; `persistSession: false`, resume нет; approvals авто-deny (или bypassPermissions); дочерней DSH-сессии не создаётся → **в Web UI виден только плоский tool-result**. «Наблюдать и поправлять исполнителя в реальном времени» через штатный DSH — невозможно по конструкции текущего rc.
- **Claude Code не может быть членом `agent-team`**: команде нужны continuable-провайдеры (`prepareContinuable` есть только у in-process spawn/fork). Максимум — Claude Code как *инструмент* члена команды.
- `agent-team` инженерно зрелый (DAG задач с CAS-ревизиями, mailbox, cold recovery, 3000 строк тестов), но `private`, **без какого-либо Web UI** (ростер/доска в браузере не отображаются), один процесс, один checkout, advisory-локи.
- Web UI: **auth отсутствует полностью** (только anti-rebinding Host-фенс), single-user, без TLS.
- Позитив: OpenRouter подключается чистой конфигурацией (`llm-pi-ai`, hand-declared route: `api: openai-completions`, `baseURL`, `models`, `compat`); подписочный OAuth Claude Code наследуется драйвером через `HOME` (env-скраббер вырезает `*KEY*/*TOKEN*`, но `~/.claude` работает); модель координатора задаётся per-process/per-session (per-agent — нет).
- Идеи, которые стоит забрать независимо от выбора: append-only session log как единственная истина + производная история; «done» как состояние внешнего мира; журнал доставки с состояниями.

## R4. yao (Yao Agents)

- **Claude Code поддержан нативно и всерьёз**: раннер `agent/sandbox/v2/claude/` запускает CLI с `--input-format stream-json --output-format stream-json --include-partial-messages`, сессии `--session-id`/`--resume` (UUID детерминирован от assistantID+chatID), исполнение в персистентной Docker-песочнице (desktop, терминал, ФС, браузер, VNC; образ `yaoapp/sandbox-claude`). Это ровно то, чего нет в DSH: **стриминг и возобновляемость внешнего Claude Code**.
- **Но аутентификация — судя по коду, только `ANTHROPIC_API_KEY` + `ANTHROPIC_BASE_URL`** (через connector). OAuth-подписка не подтверждена и не опровергнута. Есть A2O-прокси (Claude Code поверх чужих моделей через подмену BASE_URL). **Прямое столкновение с C-Н1 (только подписка)** — ключевая неопределённость; проверяется практическим спайком (можно ли смонтировать `~/.claude` в песочницу).
- Лицензия: модифицированный Apache 2.0 — для одного пользователя self-hosted свободно; несъёмный брендинг, **обязательная «логика верификации сертификата»** в продукте, порог коммерческой лицензии 50 сотрудников/$1M, условия могут меняться односторонне.
- Модели: OpenRouter в пресетах есть; Ollama; шесть слотов (Default/Heavy/Light/Vision/Audio/Embedding).
- API: OpenAI-совместимый completions на «робота» + execute с поллингом; Mission Control (5-стадийный пайплайн со статусами, интеграции Telegram/Discord/WeChat). **API канбан-доски документацией не подтверждён.**
- Мобильность: Android beta, desktop Tauri; iOS/PWA не подтверждены; «полноценное управление с телефона» не проверено независимо.
- Зрелость: rc каждые 1–3 дня (rc8→rc15 за месяц), рефакторинги ядра между rc, 4 открытых issue (обсуждение, видимо, в китайских каналах), доки в переезде (сайт 404, читали из GitHub). Развёртывание: один Go-бинарь + Docker для песочниц; готового compose в доках нет.

## Сводные выводы для Design

1. **DSH как панель управления Claude Code-агентами сегодня непригоден** (R3): исполнитель невидим и невозобновляем. Пригоден как источник идей и как возможная платформа *позже* (ядро уже растит интеграцию Claude Code — R2).
2. **yao — единственная готовая платформа, реально стримящая и возобновляющая Claude Code**, и попадает в «self-hosted + панель + мобильность». Против него: неподтверждённая работа с подпиской (риск C-Н1), rc-темп, лицензионные особенности, недоказанный API доски и мобильное управление, C7 (wiki-линки/бэклинки) не проверен.
3. **Собственный тонкий оркестратор** (эволюция agent-dashboard: headless `claude -p --resume` + stream-json + подтверждаемая доставка + доска) технически ничем не заблокирован — все примитивы официально поддержаны (R1); это самый совместимый с C-Н1 путь, ценой разработки UI/доски/памяти самим.
4. Материальная неопределённость, требующая **практического спайка до решения**: (а) yao + подписочный OAuth (монтирование `~/.claude` в песочницу); (б) поведение нескольких параллельных headless-сессий под Max 20x.
5. Research **не отменяет** discovery: проблема и ограничения в силе. Уточнение сил: F4 (незрелость) подтверждена фактами для обоих кандидатов; C-Н1 конфликтует с SDK-путём и, возможно, с yao.

## Спайки S1–S2: результаты (2026-08-20, исполнено)

- **S1a — подписка в контейнере: УСПЕХ.** Чистый `node:22-bookworm`, `.credentials.json` смонтирован read-only, `ANTHROPIC_API_KEY` не задан → `claude -p` ответил, `is_error:false`, модель `claude-opus-5`. Подписочный OAuth переносится в контейнер монтированием одного файла.
- **S2 — параллельные сессии: УСПЕХ.** Три одновременные headless-сессии на одной подписке Max 20x — все ответили без ошибок; остаток лимитов читается программно (`~/.claude/rate-limits.json`: 5h 26%, 7d 58% на момент теста).
- **S1b — yao-песочница: УСПЕХ с оговорками.** В родном образе `yaoapp/sandbox-claude` подписочный OAuth работает (креды доставлены с правильным владельцем `sandbox`; при прямом ro-монтировании файл не читался из-за несовпадения uid, а CLI **молча выходил с кодом 0** — ловушка для будущей обвязки). По исходникам раннера: блок инъекции `ANTHROPIC_API_KEY/BASE_URL` выполняется только при `req.Connector != nil` — раннер без коннектора не трогает авторизацию.
- **Оговорки к S1b:** (1) проверен образ + код раннера, но не полный контур движка — допускает ли UI/валидация yao ассистента без коннектора, не подтверждено (нужен пилот с реальным Yao Engine); (2) если коннектор задан — env `ANTHROPIC_API_KEY` перекроет подписку; (3) образ несёт устаревший Claude Code 2.1.33 — потребуется свой образ; (4) доставка кредов в персистентную песочницу — отдельный механизм (root-install/uid-маппинг).

**Вывод:** страх «подписка на сервере невозможна» опровергнут для обоих кандидатов (A и B). Ворота A открыты условно — остаётся проверка на уровне движка (пилот).
