## 1. Выбранная альтернатива

**A: канон знаний и памяти — в Postgres Гефеста + pgvector как спроектированная дверь с включением по замеру.**

1. **Хранение:** таблицы памяти в Postgres рядом с оперативным каноном (D-2): записи со скоупами (глобальный / проект / роль), классами (правило, ловушка, learning, справочник, карточка, журнал), слоем recall (ядро/тело), автором, ревизиями, русским FTS (`to_tsvector('russian')` — эксплуатационно доказан в agent-dashboard). Wiki-линки/бэклинки — таблица связей + резолвер (общие с С7-слоем). **Вес/фильтр по классу в recall-выдаче** — колонка схемы с первого дня (журнал — с понижающим весом).
2. **Recall — трёхслойный (Р-1), оба верхних слоя с бюджетами:**
   - **ядро** — правила, ловушки, процессные инструкции; бюджет **≤ 12 КБ байт UTF-8 итогового текста (без индекса)**; при превышении генератор **падает громко** (не молчаливое усечение); приём новой записи в полное ядро требует одновременного вытеснения — панель показывает бюджет и предлагает, решение — владельца;
   - **индекс** — аннотации канона, бюджет **≤ 16 КБ**, автоматическая проверка как у ядра; **классы «карточка» и «журнал» в индекс-инжекцию не попадают** (только recall-by-need); журнал старше 30 дней — агрегатной строкой;
   - **тело** — recall-by-need через MCP/CLI с **авторизацией по скоупу**: записи скоупа проекта читаются только сессиями этого проекта; классы «карточка»/«журнал» — только сессиям владельца/панели.
3. **Подъём (C-П1, ред. 2):** хук конца сессии собирает кандидатов, **копируя сырьё в таблицу кандидатов в момент предложения** (worktree умирают раньше редакции); дополнительный скан осиротевших memory-каталогов ловит аварийные сессии (хук на крешах не срабатывает). **Редактор канона — владелец**: панель показывает список кандидатов с действиями «принять / отклонить / править»; след решения — в журнале. Мастер-агент как LLM-редактор **исключён** (решение владельца: рост расхода не оправдан; заодно снята атака B-4 — LLM-галлюцинация не может попасть в ядро). Автоматика ограничена сбором и opt-in дедуп-подсказом (только нечувствительные классы, см. п. 7). **Алерт**: кандидатов в статусе «предложено» больше 20 или старше 7 дней → уведомление владельцу. **Редакционная политика** (критерии ядра, формат ловушки, порог дедупа) — сама запись канона класса «правило»: смена того, кто/что помогает редактировать, не меняет критериев.
4. **Выгрузка вниз (C-П2, F-П6):** генератор кладёт производные файлы из канона — фрагменты ядра+индекса для SessionStart и memory-файлы роли в рабочие cwd. Правила: **через прослойку CLI** (мандат ADR-0001 расширен на файловые форматы `~/.claude`); в шапке каждого выгруженного файла — **маркер происхождения и ревизия канона**; детектор дрейфа «выгрузка старше N часов при изменённом каноне» — алерт; генерация по хуку создания worktree, не по расписанию; файлы без нашего маркера не трогаем, `MEMORY.md` не перезаписываем (образец yao-genfile — docs/06-yao-iznutri.md §1.6); генератор проверяет ожидаемую структуру каталога памяти harness и при несовпадении **падает громко**. **Фазирование:** шаг 1 — только «ядро+индекс» через SessionStart-хук; шаг 2 — мост «роль → cwd», когда генератор пожил.
5. **pgvector — дверь, не двигатель (честная формулировка после B-7):** расширение установлено; отдельная таблица `memory_embeddings (entry_id, model, dim, vector)`; **до включения** размерность не зафиксирована. **Включение = фиксация размерности + backfill + построение индекса (ivfflat/hnsw); смена embedding-модели после включения = повторный embed корпуса** — цена признана. Триггер включения — замер: **промах = пустой ответ ИЛИ `miss=true` от агента в MCP-ответе ИЛИ повторный запрос с перекрывающимися термами в течение 10 минут той же сессии**; доля = промахи / все recall-вызовы за скользящие 7 дней; порог 10%; **отчёт — пункт квартальной ревизии GF-4** (не пассивный триггер). Двигатель — локальная мультиязычная модель (класс e5-multilingual, CPU); если качество русского окажется недостаточным — граница пересмотра 4.2.
6. **Recall-лог:** запрос + id найденных записей + счётчик + `miss`-флаг, **без тел ответов**; retention 6 месяцев; входит в pg_dump.
7. **Приватность фоновых задач (правило, не дисциплина):** записи классов **«карточка» и «журнал» и записи скоупов клиентских проектов не покидают Postgres ни одной фоновой LLM-задачей** — консолидация/дедуп для них либо локальные (без LLM), либо не выполняются. Фильтр классов — в fail-loud конфиге (по образцу `default_ome.toml` EverOS — research R3: опечатка ключа = ошибка старта). Для остальных классов фоновые LLM-задачи — opt-in, бесплатный OpenRouter.
8. **Дневники (Р-2):** входят в канон классом «журнал»; плагин remember остаётся локальным писателем; подъём — штатным конвейером с честным лагом: **дневник дня доступен поиском после подъёма (обычно на следующий день)**, свежайший срез — локален.
9. **Переходный период (правило):** **vault — истина до дня переключения SessionStart-хуков; в этот день vault замораживается на запись** (не постепенно); перед выводом vault — **сверка контента** vault ↔ канон (не только restore). Предусловие переключения хуков: CLI умеет create/edit/list по классам (иначе владелец теряет доступ к правке).
10. **Переносимость (страховой полис):** **штатный автоматический экспорт канона в файлы** (markdown + frontmatter, поэнтрийно, включая ревизии) — только на self-hosted/локальный носитель, классы «карточка»/«журнал» — по отдельному флагу; restore из экспорта проверяется — тем же стандартом, что restore pg_dump.
11. **EverOS — отклонён как зависимость** (три блокера research: русский поиск мёртв в бесплатном режиме — jieba режет кириллицу посимвольно, подтверждено исполнением; стек SQLite+LanceDB архитектурен; интеграции с Claude Code нет); принят как донор идей: entry-id, поэнтрийная переиндексация, durable-очередь, цикл recall→capture→flush, fail-loud конфиг.

## 2. Почему это решение

- **Один источник истины буквально (C-Н5):** память в той же СУБД, что задачи/журнал; принцип «база — истина, файлы — выгрузка» распространён на память; каскад согласованности существует только в одну сторону (вниз) и оснащён маркерами ревизии и детектором дрейфа.
- **Русский поиск доказан, не обещан** (agent-dashboard `documents` — в эксплуатации).
- **Ноль новых сервисов (F7)**; редактор — владелец: дешевле и надёжнее LLM-редактора (blast radius ядра требует человека).
- **pgvector по замеру** с наблюдаемым (а не пассивным) триггером и признанной ценой включения.
- **Приватность правилом, не дисциплиной**: чувствительные классы не покидают Postgres.

## 3. Что мы отдаём (принятые минусы)

- Правка знаний — через панель/CLI (не Obsidian); смягчение — штатный файловый экспорт (п. 1.10).
- Git-истории знаний нет — ревизии в БД + поэнтрийный экспорт.
- Векторный recall не с первого дня; включение потребует фиксации размерности и re-embed при смене модели.
- Редакционная нагрузка — на владельце (~2–4 ч/нед батчем по алерту); цена осознана («лучше я сам»).
- Мост «роль → cwd» — наша механика на движущейся стороне harness; смягчения — прослойка CLI, громкие падения, фазирование.
- Миграция: скрипт — дни; **редакционный проход (классификация, дедуп, формирование ядра) — 1–2 недели фонового внимания владельца**. Ядро формируется редакционно, не маппингом всех статей (35 статей >> 12 КБ — вытеснение начинается в день один, и это нормально: в ядро идёт выжимка).

## 4. Границы пересмотра

1. Триггер замера сработал → включение векторной ноги (предусмотренный путь).
2. Локальная embedding-модель не тянет русский → пересмотр способа (платный API против правки C-Н1 — решение владельца).
3. EverOS открывает апстрим + русский first-class → пересмотр границы «донор идей» (проверяет GF-4; там же — слежение за встроенной памятью harness: если Claude Code отрастит кросс-проектную память, пересмотреть подъём и C-Н5).
4. Канон > ~5–10 тыс. записей и FTS/бэклинки деградируют → пересмотр индексного слоя.
5. Редактирование владельцем становится узким местом (алерт очереди срабатывает регулярно) → пересмотр редакционной модели (в т.ч. возврат к идее агента-помощника с diff-предложениями — уже с бюджетной оценкой).
6. Появляется зрелый открытый memory-стандарт (две независимые реализации) → пересмотр recall-интерфейса; схема держит интерфейс отделённым от внутренностей.

## 5. Операционные последствия

- Схема памяти проектируется **вместе с D-2**; входы из этого решения: скоупы, классы, слои, бюджеты, вес класса в выдаче, таблица кандидатов (с копией сырья), embeddings-дверь, авторизация recall по скоупу, recall-лог, операция **«удалить с производными»** (запись + ревизии + индексы + перегенерация выгрузок + вычистка recall-лога).
- SessionStart-хуки переключаются с vault-инжекции на выгрузки канона — в день заморозки vault (п. 1.9).
- Логирование recall (метаданные) — с первого дня; отчёт «доля промахов» — в панели и в повестке GF-4.
- Бюджеты ядра и индекса — автоматические проверки.
- Дедуп-подсказ и любые фоновые LLM-задачи — opt-in, фильтр чувствительных классов в конфиге, бесплатный OpenRouter.
- Экспорт канона в файлы — по расписанию, restore проверен.

## 6. План (вливается в фазы Гефеста)

1. ADR-0003 принят → вход в **D-2 (схема данных)**.
2. Ф1: таблицы памяти + FTS + MCP/CLI recall (+авторизация по скоупу) + recall-лог + CLI create/edit/list.
3. Ф1–Ф2: SessionStart-выгрузка «ядро+индекс» (шаг 1 моста), панель кандидатов с принять/отклонить/править, алерт очереди, файловый экспорт.
4. Ф2: миграция (скрипт + редакционный проход), день переключения хуков = заморозка vault на запись, сверка контента, вывод vault. Затем шаг 2 моста — memory-файлы ролей по worktree-хуку.
5. По триггеру: pgvector (фиксация размерности + backfill + индекс).

## 7. Критерий выполненности

- ADR-0003 принят; входы для D-2 зафиксированы.
- Агент любой роли на любом cwd получает при старте ядро+индекс из канона (не из vault); бюджеты обоих слоёв проверяются автоматически; тело — по запросу через MCP/CLI с авторизацией по скоупу.
- Роль помнит своё между worktree и машинами (после шага 2 моста); выгруженные файлы несут маркер и ревизию канона; детектор дрейфа работает.
- Learning из сессии проходит путь: кандидат (сырьё скопировано) → список в панели → решение владельца → канон → виден в следующих стартах; след в журнале; алерт очереди работает.
- Дневник дня доступен поиском после подъёма (лаг признан); vault заморожен, сверен и выведен.
- Recall-лог (метаданные) накапливается; отчёт «доля промахов» в панели; пункт в повестке GF-4.
- Файловый экспорт канона выполняется по расписанию; restore из него проверен один раз руками.
