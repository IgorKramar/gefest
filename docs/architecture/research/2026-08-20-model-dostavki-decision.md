## 1. Выбранная альтернатива

**A: push раннером + delivered-по-потоку, с C-дверью (`requires_ack` — альтернатива C design, push+ack)**:

1. **Транспорт:** раннер владеет stdin каждого живого исполнителя; указание пишется в stdin в любой момент (S4: очередь CLI доставляет на границе шага, поток цел; S5: очередь >1 — FIFO, склейка в одно продолжение). Запись — через writer per-сессия; writer сериализует запись и SIGTERM (EPIPE — штатная ветка: указание возвращается в `queued`). `stop` = SIGTERM (документировано: abort хода, terminate дерева Bash, SessionEnd-хуки, exit 143, сессия сохраняется); раннер дописывает финальное событие хода в журнал ADR-0005 со статусом `interrupted` (CLI при SIGTERM может не выдать `result`). **Stop инвалидирует очередь:** все `queued`/`sent`-без-delivered указания сессии переводятся в `cancelled_by_stop` — «прерви сейчас» не превращается в «доиграй потом» (B-5). В вехах и UI «стоп» — класс прерываний; SIGTERM — сегодняшняя реализация (CC-8).
2. **Состояния указания:** `queued` → `sent` (записано в stdin живого процесса, факт+время) → `delivered` → терминальные исходы в `command_deliveries` (append-only, ADR-0005). **Каузальный delivered (CC-1, спайк S5):** запись в простое — delivered по началу любой новой активности потока; запись mid-turn — delivered только по активности, начавшейся **после** `tool_result` инструмента, который был in-flight на момент записи; error-события не подтверждают; таймаут наблюдателя — настройка `delivery_confirm_timeout` (старт: 120 с сверх текущего tool-вызова). `num_turns` маркером не является (S5). **Reconciliation:** процесс умер — **всё** `sent` без каузального delivered перекладывается в `queued` (выбор «дублируем, не теряем», B-2); порядок повторного вручения — FIFO по времени постановки; дедуп — раннером по uuid указания (не вручать один uuid дважды в одну живую сессию), инструкция модели «игнорируй дубль» — второй эшелон, не опора. At-least-once — потолок, exactly-once не обещаем.
3. **C-дверь:** поле `requires_ack` (по умолчанию false): при true `delivered` требует MCP-вызова `inbox_ack(uuid)`. **В v1 — только решение, кода нет** (колонка, инструмент, таймеры — по первому реальному классу указаний, право forward-миграции ADR-0005). **Бюджет двери: больше 2 классов с ack = пересмотр D-4**, а не очередное включение (F-2).
4. **Сон до ответа (C-Д4а):** блокирующий вопрос → ход завершается → сессия `waiting_answer`; вопрос фиксируется событием session_events (под scope_class и retention ADR-0005). **v1 — контейнер не останавливается** (процесс в простое токены не жжёт; RAM 1–2 ждущих — копейки; подтверждено владельцем): спящий = живой процесс, reaper знает состояние `sleeping` и не трогает. Стоп-по-таймауту — код за флагом, включается при >2 одновременно спящих, с двухфазным барьером: `stopping` в таблице блокирует вручения → ответ падает в `queued` → после остановки `sleeping_cold` → ответ будит resume-ом; гонка «ответ во время остановки» (B-6) исключена барьером. «Resume не взлетел» (перезагрузка хоста, битый транскрипт) → путь ретрай-машины: чистый рестарт с повторной доставкой вопроса+ответа в свежий контекст.
5. **Планировщик (v1 упрощён, подтверждено владельцем):** глобальный потолок 5 + 1 ручной слот владельца; порядок — FIFO (колонка `priority` в схеме с v1, приоритетная сортировка и пер-ролевые квоты — итерация 2 по данным панели). Каждое решение планировщика объяснимо: лог решений + поле **«почему стоит»** (`quota`/`limit`/`probe`/`sleeping`) у указания в панели (H-2, H-5). **Лимиты — двухосевая политика** (5h-окно + weekly; weekly исчерпан → стоит всё + уведомление; оси — конфиг, F-6): по `system/api_retry` (rate_limit/billing_error) очередь встаёт до `resets_at` (best-effort из `~/.claude/rate-limits.json` на хосте, копия у раннера — не в контейнере), fallback — экспоненциальная проба: пробное возобновление одной задачи через 5 мин, интервал ×2 до потолка 60 мин, до первого успеха. Ручной слот минует паузу 5h-окна; при жёстком отказе API ручной команде — состояние `limit_blocked` + уведомление владельцу (не ретраи, B-7). Метрика голодания фона (возраст старейшей ждущей фоновой задачи) — в панели, детектор границы пересмотра слота. Слот — per-operator настройка, инвариант: сумма ручных слотов ≤ резерв (F-4). Из api_retry-вех в БД — белый список полей (категория, error_status, retry-счётчик, resets_at, метки времени); остальное — в raw-файл вне БД (C-5).
6. **Ретраи (C-Д5а):** сбой сессии не по лимитам → **в v1 один авто-ретрай** чистым рестартом → задача `paused` + инцидент (журнал + алерт владельцу); до 3 ретраев с выбором resume/рестарт «по типу сбоя» — итерация 2, типология сбоев — артефакт GF-2 (граница: «живой контекст» = транскрипт восстановим `--resume`). Перед авто-ретраем — сверка observations и вех: «работа, похоже, сделана» → не ретраить, синтетическое «предположительно завершено» + вопрос владельцу; side-effect-указания слепо не ретраятся (B-8).
7. **Единый инбокс (C-Д6а):** сообщения агент→агент (D-9) — те же таблицы, состояния, гарантии; вид `message` с долгим `queued` — уже в перечислении (п. легенды); адресация/права/broadcast — D-9.
8. **Приватность указаний (CC-6):** текст указания — носитель клиентских данных: таблицы команд/инбокса наследуют scope_class (фильтр ADR-0005 распространяется на них); retention тела указания и текста вопроса — 90 дней (факт и метаданные доставки — вечно); «удалить с производными» включает тексты команд; алерты и уведомления любого канала — только факт + ссылка (task_id/тип), ноль свободного текста (C-3); opt-out «Improve Claude» на аккаунте — предусловие эксплуатации (проверить руками, C-2); аутентификация ручного слота и недостижимость owner-эндпоинтов из сети исполнителей — D-7 (явная отсылка, не молчание, C-4).
9. Перечисления доставки из ADR-0005 уточняются этим решением forward-миграцией (право — ADR-0005, раздел «Правила»); итоговый список исходов — артефакт GF-2 в границах «не уже ADR-0005» (J-9).

## 2. Почему

Спайки сняли главный технический риск (mid-turn stdin работает штатно — S3/S4; FIFO и склейка очереди — S5, собственное исполнение); delivered-по-потоку — единственная модель подтверждения, не зависящая от дисциплины модели (конституционное недоверие проекта) и не жгущая токены, а каузальная привязка (активность после in-flight `tool_result`) закрывает разрыв «delivered ≈ sent+heartbeat» (B-1); DSH-словарь выбран владельцем явно; сон без остановки контейнера в v1 примиряет «нужен режим ожидания» с C-С1 дешевле, чем sleep/resume-айсберг (H-3).

## 3. Что отдаём

`delivered` — косвенное свидетельство («поток отреагировал после вручения»), не «модель осознала» (смягчение — C-дверь); interrupt посреди tool-вызова невозможен (только stop) — принято владельцем; вид limit-ошибки в stream-json не документирован — первая встреча уточнит парсер (принято, с написанным fallback-путём пробы); повторное вручение после reconciliation может дать дубль текста в контексте (дедуп раннером по uuid в живую сессию; остаточный риск — дубль в *новую* сессию после рестарта, инструкция модели — второй эшелон); транскрипты сессий с uuid указаний живут у Anthropic — канал признан ограничением, размен «форензика > нелинкуемость» осознан (C-2); S3/S4/S5 — наблюдённое поведение, не контракт: смена поколения CLI перепроверяет фундамент (F-1, смягчение — CC-8 в §5).

## 4. Границы пересмотра

Появление документированного interrupt-control в stdin (#41665, capability `interrupt_receipt_v1`) → добавление реализации в класс «стоп», пересмотр «только SIGTERM»; практика ложных delivered при каузальном наблюдателе → включение requires_ack классами, **бюджет: >2 классов = пересмотр D-4**; голодание фона по метрике из панели → пересмотр политики слота; >2 одновременно спящих → включение стопа-по-таймауту (код за флагом готов); смена правил лимитов Max (оси/геометрия) → правка конфига осей, не модели; D-9 потребует семантики сверх инбокса (broadcast, каналы, «прочитано») → расширение, не замена; обновление CLI → прогон контрактных тестов S3/S4/S5 до раскатки (версия CLI пинуется, обновление — решением).

## 5. Операционные последствия

**GF-2, ядро v1 (70 %, 4–6 недель темпа; полный §5 честно стоил бы 60–100 ч — H-1):** writer stdin per-сессия (сериализация с SIGTERM), каузальный наблюдатель delivered, SIGTERM-обвязка с синтетическим закрытием и `cancelled_by_stop`, reconciliation, **фальшивый исполнитель** (бинарь: эмитит stream-json, читает stdin, честно умирает по SIGTERM, управляемые задержки — без него тесты жгут общее 5h-окно и мигают, H-4), поле «почему стоит» + лог решений планировщика, планировщик v1 (потолок 5 + слот + FIFO), один авто-ретрай, алерт «sent без delivered > N сек».

**Итерация 2 (по данным панели):** пер-ролевые квоты, приоритетная сортировка, типология сбоев + до 3 ретраев с resume, стоп-по-таймауту за флагом, requires_ack-код.

**Подтверждено владельцем (2026-08-21):** (1) v1 без остановки спящих контейнеров; (2) v1-планировщик упрощён; (3) requires_ack в v1 — только решение, без кода.

**Тесты (против фальшивого исполнителя):** mid-turn очередь >1 (FIFO — подтверждён S5), SIGTERM во время tool-вызова (вехи корректны, очередь инвалидирована), reconciliation после kill раннера между sent и границей (перекладка + дедуп), лимит-паника (симуляция api_retry, белый список полей), каузальность (событие до записи ≠ delivered). Контрактные тесты прослойки CLI (S3/S4/S5 как код) — вход D-6, прогон при каждом обновлении CLI (CC-8).

## 6. Migration path

Ф0/GF-2 — реализация на v1-ядре схемы; уточняющие перечисления (вид command/message, `cancelled_by_stop`, `limit_blocked`, scope_class инбокса, retention) — forward-миграцией; чат D-9 подключается к готовому инбоксу.

## 7. Критерий выполненности

ADR-0007 принят; DoD Ф0 (= decision консолидации ред. 2 / GF-2, J-3) выполняется этой механикой (команда доходит с каузальным `delivered`, гашение = прерывание с инвалидацией очереди); демонстрация: указание живой сессии посреди длинного tool-вызова доставлено на границе шага и видно в панели с трассой; ответ будит `waiting_answer`-сессию (контейнер жив); лимит-пауза с работающим ручным слотом и полем «почему стоит»; авто-ретрай → paused + инцидент.
