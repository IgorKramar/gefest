# Decision summary: модель доставки (D-4)

- Дата: 2026-08-20 · Фаза: Decide (deep) · Входы: discovery (2 раунда, C-Д1а…Д6а, спайк S3), research (S4, SIGTERM, лимиты), design (A/B/C/D)
- Легенда: см. discovery цикла; «указание» — единица инбокса (команда владельца или сообщение агенту, C-Д6а); «граница шага» — момент между tool-вызовами/ходами, где CLI забирает очередь stdin (S4).
- Статус: **принято владельцем** («Подтверждаю», 2026-08-20). Ожидает roast + ADR-0007.

## Reviews

(заполняется после roast)

## 1. Выбранная альтернатива

**A: push раннером + delivered-по-потоку, с C-дверью (`requires_ack`)**:

1. **Транспорт:** раннер владеет stdin каждого живого исполнителя; указание пишется в stdin в любой момент (S4: очередь CLI доставляет на границе шага, поток цел). `stop` = SIGTERM (документировано: abort хода, terminate дерева Bash, SessionEnd-хуки, exit 143, сессия сохраняется) → синтетическое закрытие хода в наших вехах («прервано», не «завершено»).
2. **Состояния указания:** `queued` (в таблице, исполнителя нет/спит) → `sent` (записано в stdin живого процесса, факт+время) → **`delivered` (после записи поток сессии продолжился** — следующее stream-json-событие процесса**)** → терминальные исходы в `command_deliveries` (append-only, ADR-0005). Процесс умер между sent и границей шага → reconciliation перекладывает в `queued` (идемпотентность повторного вручения — по uuid указания в тексте, исполнитель инструктирован игнорировать дубль; at-least-once — потолок, exactly-once не обещаем).
3. **C-дверь:** поле `requires_ack` (по умолчанию false): при true `delivered` требует MCP-вызова `inbox_ack(uuid)` — включается точечно, если практика покажет класс указаний, где потока мало. Не общий режим.
4. **Сон до ответа (C-Д4а):** блокирующий вопрос → ход завершается → сессия `waiting_answer`; > 5 мин (настройка) → контейнер останавливается; ответ владельца → resume контейнера → указание в stdin → продолжение потока = delivered. Токены во сне не тратятся; RAM освобождается по таймауту (C-С1).
5. **Планировщик:** квоты — глобально 5 + 1 ручной слот владельца, на роль 2 (настройки, C-Д3а); приоритеты указаний/задач — колонка priority с v1 (C-Д2а); лимиты — по `system/api_retry` (rate_limit/billing_error) и таймауту потока очередь встаёт до `resets_at` (best-effort из rate-limits.json, fallback — экспоненциальная проба), фон стоит, ручной слот работает, владельцу — уведомление. Первый лимит-инцидент документирует себя: сырые error-события пишутся в вехи.
6. **Ретраи (C-Д5а):** сбой сессии не по лимитам → до 3 авто-ретраев (resume при живом контексте, чистый рестарт при мёртвом — по типу сбоя), затем задача `paused` + инцидент (журнал + алерт владельцу).
7. **Единый инбокс (C-Д6а):** сообщения агент→агент (D-9) — те же таблицы, состояния, гарантии; адресация/права — D-9.
8. Перечисления доставки из ADR-0005 уточняются этим решением forward-миграцией (право заложено ADR-0005 §CC-9).

## 2. Почему

Спайки сняли главный технический риск (mid-turn stdin работает штатно — S3/S4, собственное исполнение); delivered-по-потоку — единственная модель подтверждения, не зависящая от дисциплины модели (конституционное недоверие проекта) и не жгущая токены; DSH-словарь (граница шага) выбран владельцем явно; сон с остановкой контейнера примиряет «нужен режим ожидания» с C-С1.

## 3. Что отдаём

`delivered` — косвенное свидетельство («процесс жив и работает после вручения»), не «модель осознала» (смягчение — C-дверь); interrupt посреди tool-вызова невозможен (только stop) — принято владельцем; вид limit-ошибки в stream-json не документирован — первая встреча уточнит парсер (принято); повторное вручение после reconciliation может дать дубль текста в контексте (инструкция игнорировать + uuid — дисциплина модели в узком месте, признано).

## 4. Границы пересмотра

Появление документированного interrupt-control в stdin → пересмотр «только SIGTERM»; практика ложных delivered (поток продолжился, указание проигнорировано) → включение requires_ack классами; очередь ручного слота конфликтует с фоновой (владелец жжёт окно) → пересмотр политики слота; D-9 потребует семантики сверх инбокса (broadcast, каналы) → расширение, не замена.

## 5. Операционные последствия

GF-2 реализует: writer stdin per-сессия, наблюдатель потока (delivered/timeout), планировщик (квоты/приоритеты/лимиты/ручной слот), SIGTERM-обвязку с синтетическим закрытием, sleep/resume контейнеров, ретрай-машину. Тесты: mid-turn очередь >1 сообщения (FIFO?), SIGTERM во время tool-вызова (вехи корректны), reconciliation после kill раннера между sent и границей, лимит-паника (симуляция api_retry).

## 6. Migration path

Ф0/GF-2 — реализация на v1-ядре схемы; уточняющие перечисления — forward-миграцией; чат D-9 подключается к готовому инбоксу.

## 7. Критерий выполненности

ADR-0007 принят; DoD Ф0 из ADR-0001 выполняется этой механикой (команда доходит с `delivered`, гашение = прерывание); демонстрация: указание живой сессии посреди длинного tool-вызова доставлено на границе шага и видно в панели; спящий агент разбужен ответом с остановленного контейнера; лимит-пауза с работающим ручным слотом; 3 ретрая → paused + инцидент.
