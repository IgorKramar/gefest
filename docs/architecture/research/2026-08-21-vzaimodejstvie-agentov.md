# Discovery: взаимодействие агентов и чат (D-9)

- Дата: 2026-08-21 · Масштаб: standard · Входы: O-7; запрос владельца «чат для всех агентов» (D-3, раунд 2); ADR-0007 (единый инбокс, `command` ≠ `message`, message ждёт `queued` без эскалации и пробуждения); F-3 roast D-4 (broadcast, «прочитано» ≠ «доставлено», спящий адресат); ADR-0006 (общий канал агентов — только через Гефест)

## Problem

Агенты работают в изолированных контейнерах и не видят друг друга. Нужны: адресные сообщения агент→агент (mailbox), общий канал «для всех» (чат), права (кто кому и что), передача работы, видимость всего этого владельцу в панели — поверх уже решённой механики доставки.

## Forces

- Экономика C-С1/подписки: сообщение не будит спящего и не жжёт токены на поллинг; чат не должен превращаться в «каждый агент перечитывает всё каждым ходом».
- Уже решено: доставка message = тот же инбокс, `queued` до естественного пробуждения; таблицы/гарантии общие (ADR-0007 п.7).
- Приватность: тексты сообщений агентов — тот же класс, что вехи: scope_class, retention (ADR-0005/0007); в алерты — факт+ссылка.
- Отвлечение: push чужого сообщения mid-turn ломает фокус работающего агента; но неполученное вовремя «стоп, это уже сделано» — потерянные токены.
- Владелец видит всё и участвует с панели; аудит различает владельца и агентов.
- Мастер-агент/редактор канона (ADR-0003) и будущие роли kst — потребители того же канала.
- D-16 (MCP-поверхность) даст инструменты; D-9 задаёт семантику, не транспорт.

## Existing constraints

Интерим ADR-0005: запись агента — только события своей сессии; `assign` — только владельцу. Схема: journal (author/addressee), commands/deliveries, session_events — доноры; новые таблицы — forward-миграцией.

## Open questions (владельцу)

- **Q1. Топология чата:** один общий канал для всех агентов + адресные mailbox (v1, комнаты per-project — дверь) — или сразу каналы-комнаты? Твоя формулировка была «чат для всех агентов» — читаю как один канал, подтверди.
- **Q2. Как агент получает:** (а) адресные `message` — push в stdin (механика указаний), чат — только pull MCP-инструментом на границах хода; (б) всё pull — агент сам решает, когда читать (дисциплина модели — против конституции); (в) всё push, включая чат (шум в контексте каждого). Рекомендация — (а): адресное — важное, доставляем; чат — фоновая координация, читается когда агент готов.
- **Q3. «Прочитано»:** нужен ли маркер `read` для message (агент вызвал чтение) отдельно от `delivered` (легло в контекст)? Панель тогда показывает «доставлено, но не прочитано» у чата. Цена — ещё одно состояние; F-3 считает нужным.
- **Q4. Права адресации:** любой агент пишет любому и в чат; broadcast-указания («всем: стоп») — только владелец. Так — или жёстче (писать только в рамках общего проекта/задачи)?
- **Q5. Роль без живой сессии:** message роли, у которой нет запущенной задачи, ждёт первого запуска этой роли (может — днями). Показываем владельцу «у роли N непрочитанных» и даём кнопку «запустить/передать мне» — достаточно? Или нужна эскалация по возрасту?
- **Q6. Передача работы:** агент хочет передать подзадачу другой роли — через предложение владельцу (`pending` → подтверждение, как ресурсы/память) в v1, автопередача в доверенных парах — дверь D-16? Или сразу автопередача?
- **Q7. Владелец в чате:** твои сообщения в общем канале — обычные message (без гарантий указаний) или всегда указания (со всей машиной delivered)? Рекомендация: в чат — message, адресно агенту — указание.

## Success criteria

Агент может сказать другому «не трогай миграции, я в них» без владельца-посредника; владелец видит всю переписку в панели; спящие не будятся и токены не жгутся; права и след — по построению; GF-2+ реализует без новых решений.
