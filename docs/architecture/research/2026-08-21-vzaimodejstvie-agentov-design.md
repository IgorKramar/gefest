# Design: взаимодействие агентов и чат (D-9)

- Дата: 2026-08-21 · Масштаб: standard · Вход: discovery + ответы владельца (Q1–Q7). Research пропущен: version-sensitive утверждений нет, семантика строится на собственной инфраструктуре.

## Общая часть (из ответов владельца)

- **Топология (Q1):** один общий канал + адресные mailbox; комнаты per-project — дверь (channel_id в схеме с v1, активен один).
- **Получение (Q2-а):** адресный `message` — push в stdin по машине указаний (ADR-0007: `queued` до пробуждения, без эскалации доставки); чат — pull MCP-инструментом на границах хода.
- **Read-маркер (Q3):** «доставлено» ≠ «прочитано»; панель показывает непрочитанное.
- **Права (Q4):** писать (адресно и в чат) — в рамках общего проекта; broadcast-указания — только владелец. Владелец видит всё.
- **Эскалация (Q5):** message без прочтения дольше порога (настройка, старт 24 ч) → алерт владельцу (факт+ссылка) с действиями «запустить роль / переадресовать / снять».
- **Передача работы (Q6):** своему сабагенту (внутри контейнера задачи, механика Claude Code) — автоматически, Гефест не участвует; другому полноценному агенту — предложение `pending` → подтверждение владельца (образец ADR-0003/0010); автопередача доверенным парам — дверь D-16.
- **Владелец в чате (Q7):** пишет message с пометкой owner; pull отдаёт их с приоритетной маркировкой, инструкция ролей — разбирать первыми; для гарантий — «отправить как указание» рядом в панели.
- **Приватность:** тексты чата/mailbox — таблицы под scope_class, retention тела 90 дней (политика указаний ADR-0007 п.8); в алерты — факт+ссылка.

## Развилка: носитель чата

**A. Чат — отдельный append-only поток + курсоры читателей.** `chat_messages (channel_id, version)` — один поток; каждый агент-читатель — курсор (паттерн consumer_offsets ADR-0005); `read` = продвижение курсора при pull; mailbox — единый инбокс ADR-0007 (push, delivered + отметка read при чтении инбокса). Новый агент читает канал с любого места — история доступна.

**B. Всё через единый инбокс с fan-out.** Сообщение в чат = N адресных message (по deliveries на каждого агента); read — исход в deliveries. Один механизм на всё, но объём записей ×N, состав «всех» фиксируется в момент отправки — новый агент истории не получает, «все» надо пересчитывать.

**C. Статус-кво.** Координация только через владельца (сообщение → владелец → указание). Ничего строить не надо; владелец — узкое место и единая точка задержки; боль «агенты друг друга не видят» остаётся.

| Критерий | A: поток + курсоры | B: fan-out инбокса | C: статус-кво |
|---|---|---|---|
| Объём записей | 1 сообщение = 1 строка | ×N агентов | 0 |
| Новый агент / история | Курсор с нуля — вся история | Нет истории до появления | — |
| Read-маркер (Q3) | Курсор — естественно | Исход в deliveries | — |
| Пропуски | Gap-detection потока (ADR-0005) | Отдельно на каждого | — |
| Механизмов | 2 (поток + инбокс) — но оба уже есть в схеме | 1 | 0 |
| Права per-project (Q4) | Фильтр на pull по проекту | В момент fan-out | — |
| Владелец-узкое-место | Нет | Нет | Да |

**Lean автора — A**: «второй механизм» — иллюзия, поток `(stream_id, version)` с курсорами уже конституция схемы (ADR-0005), чат — ещё один поток, а не новая конструкция; fan-out B платит ×N записей за то, что A получает курсором бесплатно, и теряет историю для новых участников — а история чата и есть координационная ценность («что уже решили»). C отвергается целью цикла.

Не рассматривалось: внешний мессенджер/шина как чат (антипаттерн ADR-0006 «общий канал — только через Гефест»); push чата в stdin всем (Q2-в отклонён владельцем); отдельный чат-сервис (F7, C-С1).
