# Pragmatist: схема данных Гефеста (D-2)

**Target**: docs/architecture/research/2026-08-20-shema-dannyh-decision.md
**Date**: 2026-08-20

## Summary

Решение A операционно честное — для команды из трёх. Для одного оператора с 1–2 ч/день «1.5–2 недели» = 1.5–2 месяца календаря, и весь срок — двойной учёт с AD. Главные риски не в схеме, а в трёх отсутствующих вещах: деплой миграций под третьей ролью, физическая чистка файлов сырья, действие при расхождении state с журналом.

## Operational findings

### H-1: «1.5–2 недели» — фулл-тайм-недели, а у проекта их нет
**Category**: day-1 vs steady-state · **Severity**: high

30+ таблиц, 8–12 миграций, RLS, отрицательные и смоук-тесты — 60–80 инженер-часов (узкое место — ревью владельцем). При 1–2 ч/день = 6–10 недель календаря до первого кода GF-2; всё это время нет ни панели, ни раннера. Расхождение в 4–5 раз признать в ADR-0005 явно, иначе GF-5 «просрочена» с первого дня.

### H-2: Отладка RLS в одиночку — «пустая выборка без ошибки»
**Category**: hidden overhead · **Severity**: medium

FORCE + роли-не-владельцы: и psql владельца под политиками. Классика: ноль строк, ошибки нет, час на «забыт set_config / пул отдал соединение без контекста / NULL в current_setting». Смягчение дёшево: psqlrc-функция `login_as('owner')` + тест «NULL-контекст → пусто, а не всё» — зафиксировать в GF-5. Оценка: 2–4 инцидента по 1–3 ч в первый месяц.

### H-3: «Файлами с ротацией» — ротация названа, механизм не существует
**Category**: hidden overhead · **Severity**: medium (high в момент ENOSPC)

Кто удаляет файлы? Нужен janitor-таск (планировщика в решении нет), поведение при переполнении диска (сессия падает? раннер ретраит?), метрика диска. pg_dump файлы не видит — RPO сырья «потеряли всё» либо принимается явно, либо файлы в бэкап; сейчас ни то, ни то. Переполнение на compose-хосте с AFFiNE уронит и Postgres. Оценка: 4–8 ч в GF-5 против потерянного вечера + риска Postgres потом.

### H-4: Аудит-триггер фиксирует ночную правку, но не даёт легального пути починки
**Category**: on-call burden · **Severity**: medium

Единственному оператору в 3 ночи проще всего `UPDATE tasks ...` в psql; триггер запишет, но state разойдётся с журналом навсегда (state — не проекция). Запрещён быстрый путь — не дан санкционированный медленный: runbook «как легально починить» (корректирующее событие через `hef task fix-state`, никогда прямой UPDATE). Запрет без альтернативы у уставшего одиночки не работает.

### H-5: Три роли Postgres против «один бинарь, embedded миграции» — деплой не специфицирован
**Category**: deployment risk · **Severity**: high

Бинарь работает под `gefest_app`, владелец таблиц — `gefest_migrator`. Либо два DSN в env бинаря (разделение полудекоративное), либо отдельный шаг `hef migrate` в compose с порядком запуска. Что выбрано — не сказано; от этого зависят entrypoint, bootstrap трёх ролей на чистом хосте, поведение при упавшей миграции. Плюс: «forward-only» без слов «откат = restore pg_dump, RPO 24 ч» — плана отката нет вообще. 30 минут решения сейчас против полудня переделки при первом деплое.

### H-6: Двойной учёт AD↔Гефест длится столько, сколько длится H-1
**Category**: cost · **Severity**: medium

10–15 мин/день двойного ведения × 2 месяца ≈ 10 ч — ещё неделя темпа проекта на бухгалтерию. Цена растёт линейно с задержкой схемы — аргумент за 70%-версию.

### H-7: Lookup + Rust-enum — «расширяемо без миграции» на деле требует релиза
**Category**: operational debt · **Severity**: low

Новый статус = миграция-INSERT + вариант enum + перекомпиляция + деплой. Нормальная цена типобезопасности, но не называть «расширяемо без релиза»; CI-тест синхронизации — с первой миграции.

## What's understated in the proposal

«Недели» (H-1); «с ротацией» (H-3); «штатный sqlx migrate» (H-5); «плата в отладке» без цены и смягчения (H-2); «второй оператор политикой» — оплачивается сегодняшним каждый день.

## What's missing entirely

План отката; бэкап сырья; bootstrap хоста; runbook «state разошёлся»; планировщик retention (кем запускается batched-DELETE в одном бинаре).

## What's actually realistic

**70%-версия v1 — ядро ~14 таблиц**: actors, roles_profile, projects, project_counters, tasks, task_events, task_statuses, commands, command_kinds, command_deliveries, sessions, session_events, journal, consumer_offsets. **Отложить forward-миграциями** (двери предусмотрены, ничего не ломается): memory_* (6 таблиц — свой план Ф2 по ADR-0003), boards/board_columns/pools/pool_tasks, tags/task_tags/task_dependencies, observations/collector_health/exports_log. RLS-каркас с v1, политики — только на ядро. Это ~2/5 объёма, cutover ближе на месяц, ни одно решение не пересматривается.
