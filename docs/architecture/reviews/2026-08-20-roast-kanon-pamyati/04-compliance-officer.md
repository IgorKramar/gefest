# Compliance and security: kanon-pamyati-decision (D-8)

**Target**: docs/architecture/research/2026-08-20-kanon-pamyati-decision.md (+ discovery, research, design; ADR-0001/0002)
**Date**: 2026-08-20
**Disclaimer**: Я не юрист; окончательные правовые оценки требуют квалифицированного заключения.

## Summary

Хранение безупречно по духу приватности (свой Postgres, облачные memory-сервисы отвергнуты явно). Но у решения два противоречащих лица: discovery §4 требует «карточки людей и рабочий контекст — только свой Postgres/диск», а §1.8/§5 отправляют содержимое той же памяти в бесплатный OpenRouter фоновыми задачами — без слова о том, *что* уходит и *что не должно уйти никогда*. Вторая дыра — молчание об удалении и сроках хранения в системе, спроектированной помнить «навсегда».

## Applicable regulations and standards

Обязательства конфиденциальности перед клиентами/работодателем (главный «регулятор»); 152-ФЗ (ограниченно: «личные нужды» спорны для рабочей деятельности; трансграничная передача при внешнем LLM-процессоре — ст. 12); условия провайдеров через OpenRouter (политики хранения/обучения задаёт провайдер модели — [Provider Data Retention Policies](https://openrouter.ai/docs/guides/privacy/provider-logging)); GDPR — не применим по ранее установленному контексту.

## Findings

- **C-1 (high, third-party risk)**: содержимое памяти уходит в бесплатный OpenRouter — прямое противоречие собственному требованию приватности. Консолидация/дедуп по определению получают в промпт содержимое записей; у бесплатных моделей часть провайдеров логирует и обучается на данных, политика меняется без уведомления. Дедуп-кандидат — единственная задача, включённая по умолчанию, — работает в момент прохождения самых свежих личных памятей, включая клиентский контекст. **Закрывает**: правило в ADR «классы „карточка"/„журнал" и клиентские скоупы не покидают Postgres ни одной фоновой задачей»; ZDR/фильтр провайдеров — частью fail-loud конфига, не дисциплиной.
- **C-2 (high, retention)**: retention и путь удаления отсутствуют. Карточка человека живёт в: строке, ревизиях, FTS, будущих embeddings, аннотациях, сгенерированных файлах во всех cwd, recall-логе, бэкапах. Что значит «удалить» — не сказано. **Закрывает**: вход D-2 — операция «удаление с производными» + заявленный срок хранения дневников/карточек (хотя бы «бессрочно, осознанно»).
- **C-3 (medium, PII flow)**: ядро+индекс инжектируются в каждую сессию любой роли на любом cwd — аннотация карточки/дневника попадает в контекст сессии клиентского репозитория и далее в диалог (долговечный по Ф3). Кросс-контекстное смешение клиентов. Критерий попадания класса в индекс не задан. **Закрывает**: классы «карточка»/«журнал» в индекс-инжекцию не попадают; либо фильтр индекса по скоупу.
- **C-4 (medium, authn-authz)**: recall-by-need без модели доступа — агент в репозитории клиента A (поверхность промпт-инъекции) может достать карточки, дневники, контекст клиента B. **Закрывает**: правило видимости в D-2 (скоуп проекта; классы «карточка»/«журнал» — только владельцу/мастер-агенту), либо явное «не фильтруется — принято осознанно».
- **C-5 (medium, audit/retention)**: recall-лог с результатами — вторая нефильтрованная копия чувствительных записей вне ревизий и пути удаления. Для триггера достаточно метаданных. **Закрывает**: «лог хранит запрос + id найденных + счётчик, не тела; retention N месяцев».
- **C-6 (low, third-party)**: «read-only экспорт в git по желанию» — дверь наружу, если git внешний. **Закрывает**: «только локальный/self-hosted git, классы карточка/журнал исключены».

## What's well-handled

Хранение (свой Postgres/сервер/бэкап; облачные memory-сервисы отвергнуты с формулировкой); след редакционных решений подъёма — готовый аудит; fail-loud конфиг фоновых задач — каркас для правил C-1; ревизии и автор у каждой записи.

## Areas I couldn't evaluate

Состав промптов фоновых задач (без него C-1 — про молчание, не про подтверждённую утечку); шифрование диска/бэкапов и территориальное размещение сервера; фактическое содержимое карточек 60-people (от него зависит жёсткость квалификации по 152-ФЗ).
