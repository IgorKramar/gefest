# Pragmatist: организация монорепы (D-17)

**Target**: docs/architecture/research/2026-08-21-monorepa-decision.md
**Date**: 2026-08-21

## Summary

Раскладка трезвая — шестёрка при одном владельце и агентах-коммиттерах обслуживаема, research настоящий. Операционная проблема в двух склейках: компайл-тайм embed сцепляет каждую Rust-сборку с фронт-сборкой (платят все — bacon, CI, контейнеры агентов), а сторож `prepare --check` ловит агентов, у которых по ADR-0006 нет физической возможности починиться. Через полгода: скелет съел 2–3 недели темпа вместо «первого PR», владелец — ручной регенератор `.sqlx`.

## Operational findings

### H-1: Скелет — не «первый PR», а 15–25 часов = 2–3 недели календаря
**Category**: cost · **Severity**: medium

Покомпонентно: workspace+крейты 2–3 ч; `mise.toml` с параллельным dev 2–4 ч; CI-workflow (4 job-а, отладка циклом «пуш→жди→лог», 10–20 итераций) 4–8 ч; Dockerfile bun→chef→slim (порядок копирования `.sqlx` и `dist` между стадиями почти никогда не встаёт с первого раза) 4–8 ч; static-serve 1–2 ч. При ~10 ч/нед — весь спринт до продуктового кода. Смягчение частично заложено: `infra/` в GF-6 → первый PR ~10–15 ч.

### H-2: Embed сцепляет каждую Rust-сборку с bun-сборкой — платят все, включая агентов без фронта
**Category**: hidden overhead · **Severity**: high

«Пустой `dist` валит сборку громко» операционно значит: свежий клон, контейнер-на-задачу, CI rust-job — везде `cargo build`/`test` крейта `api` падает до `bun run build`. Path-фильтр «`crates/**` → rust-job» неверен: rust-job обязан содержать bun-стадию. Агент, правящий `runner`, платит фронт-сборку в каждом своём контейнере; bacon — то же при чистом `target/`. Механизма обхода (feature-флаг `embed-static`, заглушка-dist) в решении нет. Цена: +30–60 с на холодный build везде; ~20% таргета «≤ 5 мин» CI. Час на feature-флаг окупается за неделю.

### H-3: `prepare --check` ловит агента, который не может починиться: у него нет Postgres
**Category**: on-call burden · **Severity**: high

Регенерация требует живой БД с миграциями, а по ADR-0006 docker исполнителю не выдаётся, Postgres в контейнере задачи не описан. По построению: агент меняет запрос в `db` → CI красный → агент физически не может починить → владелец руками гоняет prepare и докоммичивает `.sqlx`. На фазе GF-5 изменения SQL — основной поток: 3–5 вмешательств/нед × 10–15 мин из 10-часового бюджета. Решить до первого агентского PR в `db`: Postgres в образе исполнителя / доступная агенту задача prepare / регламент «SQL меняет только владелец».

### H-4: Корневой Cargo.toml + Cargo.lock + «актуальная ветка» = ручной merge train
**Category**: operational debt · **Severity**: medium

`workspace.dependencies` делает корневой Cargo.toml горячим файлом всех коммиттеров; ворота ADR-0012 требуют актуальную ветку — каждый мерж инвалидирует открытые PR, ребейзы с классическими конфликтами Cargo.lock, повторные прогоны (до 2× GHA-минут при 3 параллельных PR). Смягчение дёшево: «зависимости добавляет владелец / отдельным PR первым в очереди».

### H-5: Пин sqlx-cli размазан по местам, а sqlx 0.9 — в фазе переезда
**Category**: operational debt · **Severity**: low

Версия пина фактически живёт в CI-workflow, `mise.toml` и инструкции, версия крейта — в `workspace.dependencies`; двигаться обязаны синхронно, дрейф ловится только падением prepare. Одно место-источник (например, `mise.toml`, откуда читает CI) снимает почти даром. ~1 ч × 2–4 раза/год.

### H-6: Кэш-бюджет GHA один на всех — слои chef и rust-кэши вытесняют друг друга
**Category**: tooling · **Severity**: medium

`type=gha` живёт в общем лимите 10 ГБ с кэшем `target/` и Bun; через пару месяцев — тихая деградация «5 мин или 20, как повезёт», без красного. Плюс mise-setup в каждом job-е ~30–60 с — кэшировать отдельно. Полчаса на приоритизацию кэшей при первых признаках; триггер для календаря.

## What's understated in the proposal

«Переезд на just — механический» (§3) — не бывает механическим, когда рецепты вросли в CI/инструкции/runbook, а dev-рецепт (ради которого выбран mise) — наименее тривиальный. «Пустой dist валит громко» (§1.4) — валит и того, кому фронт не нужен (H-2). «Церемония смягчена workspace.dependencies» (§3) — взамен создан горячий файл (H-4). «Кэш слоями chef» (§1.7) — общий 10-ГБ бюджет умолчан (H-6). «Первый PR, прошедший собственные ворота» (§6) — курица-и-яйцо: required checks нельзя включить до первого прогона workflow; ворота настраиваются в два приёма (30–60 мин недоумения, если не знать).

## What's missing entirely

Dev-связка vite ↔ axum (прокси на API, порты, cookie owner-листенера) — без неё рецепт `dev` не работает в принципе; обход embed в dev/test (feature-флаг, ~1–2 ч несписанной работы); runbook на красный `prepare --check` — самый частый будущий отказ CI без единого абзаца; `rust-toolchain`-пин / согласование версий Rust между машиной владельца, контейнерами и CI (mise закрывает, только если Rust явно в `mise.toml` — не сказано); единый источник версии sqlx-cli (H-5).

## What's actually realistic

То же решение, но три PR вместо одного + две дешёвые страховки. PR-1: workspace + пустые крейты + `mise.toml` + CI без docker-job (+ `rust-toolchain`-пин + однострочный runbook `prepare --check` в README `db`). PR-2: dev-контур целиком — vite-прокси, bacon, **feature-флаг `embed-static`** (dev выкл, релиз вкл). PR-3 (= GF-6): Dockerfile + chef + `type=gha`. H-3 решить регламентом до первого агентского PR в `db` — временно годится «SQL-запросы меняет только владелец»: честнее, чем ловить агентов сторожем, о который они гарантированно разобьются.
