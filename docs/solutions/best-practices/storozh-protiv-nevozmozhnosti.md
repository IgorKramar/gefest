# Сторож против невозможности: у автоматической проверки должен быть честный путь прохождения

## Context

Принцип вскрылся на roast-е решения D-17 «организация монорепы» (2026-08-21). В решении CI-сторож `cargo sqlx prepare --check` был назначен охранять синхронность `.sqlx`-метаданных с SQL-запросами — в том числе за агентами-коммиттерами, которые по ADR-0012 работают только через PR. Devil-advocate атакой B-1 показал, что конструкция противоречива на уровне периметра: контейнер задачи по ADR-0006 не содержит docker и секретов БД, а регенерация `.sqlx` требует живого мигрированного Postgres — «Компиляция `crates/db` с изменённым `query!` в offline падает; для prepare нужен живой мигрированный Postgres» (`docs/architecture/reviews/2026-08-21-roast-monorepa/01-devil-advocate.md:15`). Формулировка, давшая принципу имя: «сторож сторожит дверь, через которую агент физически не проходит» (`01-devil-advocate.md:12`). Итоговая оценка роли: это сильнейшая из восьми атак, потому что «проект существует ради агентов-коммиттеров — и принятая sqlx-схема требует того, чего у агента по периметру нет. Сторож ловит не забывчивость, а невозможность» (`01-devil-advocate.md:54`).

Прагматист независимо довёл ту же находку до операционной цены (H-3): раз агент чинить красный CI физически не может, чинит владелец — «владелец руками гоняет prepare и докоммичивает `.sqlx`… 3–5 вмешательств/нед × 10–15 мин из 10-часового бюджета» (`docs/architecture/reviews/2026-08-21-roast-monorepa/02-pragmatist.md:25`). Ред. 2 decision закрыла находку как CC-1: dev-БД со схемой Гефеста в комплекте брокера ADR-0006 плюс интерим-регламент «SQL-запросы меняет только владелец» и runbook красного `prepare --check` в README крейта `db` (`docs/architecture/research/2026-08-21-monorepa-decision.md:19`); принятая форма — в ADR-0014 (`docs/architecture/decisions/0014-monorepa-domennaya-shestyorka.md:17`).

## Guidance

**Принцип: сторож против невозможности.** Автоматическая проверка (required check, CI-gate, валидатор артефактов) легитимна только тогда, когда у каждого класса участников, которых она проверяет, есть честный путь до зелёного. Сторож должен ловить забывчивость и рассинхрон — состояния, из которых участник может выйти сам. Сторож, который ловит невозможность — состояние, из которого участник по построению периметра выйти не может, — не охраняет гарантию, а генерирует обходы и перекладывает работу на того, у кого путь есть.

Чек-лист применения — для каждого gate, который ставится или уже стоит:

1. **Перечисли классы участников**, чьи изменения проходят через проверку. В неоднородном репозитории их минимум три: люди с полным доступом, LLM-агенты в ограниченных контейнерах, CI-боты (автобампы, автогенерация). Классы различаются периметром, не намерениями.
2. **Для каждого класса проверь честный путь до зелёного**: может ли участник, честно выполнив требуемое действие (перегенерировать артефакт, прогнать миграцию, обновить снапшот), получить зелёный check *внутри своего периметра*? Проверяется не «описан ли способ в документации», а «есть ли ресурс физически»: в B-1 способ (`cargo sqlx prepare`) был описан, но Postgres в контейнере задачи — нет.
3. **Если пути нет — три легитимных выхода**, в порядке предпочтения:
   - **дай ресурс**: как dev-БД клоном шаблона со схемой Гефеста в комплекте брокера, из которого `mise sqlx-prepare` берёт DSN (`2026-08-21-monorepa-decision.md:19`);
   - **сузь круг явным регламентом**: как интерим «SQL-запросы меняет только владелец» — временное сужение автономии, записанное как принятая цена (`0014-monorepa-domennaya-shestyorka.md:30`), а не молчаливое ожидание, что агент как-нибудь справится;
   - **не ставь gate** для этого класса — необязательный check или проверка только на nightly честнее, чем required check, о который класс гарантированно разбивается.
4. **Предскажи обходы.** Спроси: «что сделает участник, упёршись в красный check без пути?» Список ожидаемых обходов — диагностика: каждый обход указывает ровно на тот ресурс, которого участнику не хватает. Для B-1 предсказаны правка `.sqlx` руками, `SQLX_OFFLINE=true` в `.env`, уход на нетипизированный `sqlx::query` (`01-devil-advocate.md:15`) — все три говорят одно: нет БД для prepare.
5. **Регламент-сужение снабди условием снятия.** Интерим «SQL меняет владелец» действует «до готовности брокера» (`2026-08-21-monorepa-decision.md:19`) — сужение без срока превращается в постоянную дыру в автономии.

## Why This Matters

Проверка, которую нельзя пройти честно, не «строгая» — она эрозирует именно ту гарантию, которую охраняла. B-1 перечисляет предсказуемое поведение агента в тупике: правка сгенерированного JSON в `.sqlx` руками (артефакт больше не отражает реальные запросы — сторож зелёный, гарантия мертва), `SQLX_OFFLINE=true` в `.env` (ровно баг sqlx#3836 — флаг ломает сам prepare), уход с макросов `query!` на нетипизированный `sqlx::query` — «эрозия главной гарантии» (`01-devil-advocate.md:15`): compile-time-проверка SQL, ради которой вся sqlx-схема и строилась, исчезает из кода, формально проходящего сторожа. Обход хуже отсутствия проверки: без сторожа рассинхрон хотя бы виден, с обойдённым сторожем он сертифицирован зелёным check-ом.

Второй эффект — скрытая цена на владельце ресурса. Пока обходы не случились, тупик разруливается вручную тем единственным, у кого путь есть: H-3 оценивает это в 3–5 вмешательств в неделю по 10–15 минут из 10-часового недельного бюджета владельца — на фазе GF-5, где изменения SQL «основной поток» (`02-pragmatist.md:25`). Gate, задуманный как автоматизация, становится генератором ручной работы, причём нигде не учтённой: в конструкции она не видна, пока прагматист не посчитает. Вывод прагматиста стал формулой выбора: регламент «честнее, чем ловить агентов сторожем, о который они гарантированно разобьются» (`02-pragmatist.md:52`).

## When to Apply

- При добавлении любого **required check или CI-валидатора** в репозиторий с неоднородными коммиттерами — люди, LLM-агенты в изолированных контейнерах, CI-боты. Особенно для проверок класса «сгенерированный артефакт синхронен с источником» (`.sqlx`, lock-файлы, сгенерированные TS-типы, снапшоты): регенерация требует тулчейна или ресурса, который есть не у всех классов.
- При **проектировании песочниц и периметров** (как контейнер задачи ADR-0006: без docker, без секретов БД): каждое ограничение периметра надо прогнать против списка gate-ов, которые обитателю периметра предстоит проходить. Ограничение и сторож проектируются в разных документах и конфликтуют молча — B-1 нашёлся только на roast-е, стыковкой ADR-0006 с ADR-0012 (`01-devil-advocate.md:15`).
- При **ревью чужого gate**: вопрос «а как красный check чинит агент/бот?» — дешёвый и высокоурожайный; если ответ — «никак, починит человек», перед вами H-3 до того, как он попал в чей-то недельный бюджет.

## Examples

**До (конструкция, отклонённая roast-ом):** `prepare --check` — required check для всех PR, трогающих `crates/**`; агенты — коммиттеры только через PR (ADR-0012); контейнер задачи — без docker и секретов БД (ADR-0006). Любая агентская задача, меняющая SQL, не доходит до зелёного честным путём: сторож сторожит дверь, через которую агент физически не проходит (`01-devil-advocate.md:12,15`).

**После (принятая форма, CC-1):** честный путь дан ресурсом — комплект брокера ADR-0006 для задач над репо Гефеста несёт dev-БД клоном шаблона со схемой Гефеста, `mise sqlx-prepare` берёт DSN из комплекта; на время до готовности брокера круг сужен явным интерим-регламентом «SQL-запросы меняет только владелец» (подтверждено владельцем), а самый частый будущий отказ CI получил runbook в README крейта `db` (`2026-08-21-monorepa-decision.md:19`; `0014-monorepa-domennaya-shestyorka.md:17`). Сторож остался — исчезла невозможность.

**Контрпример-родственник из той же семьи:** каузальный `delivered` в ADR-0007 — тот же принцип в другом обличье: подтверждение обязано быть каузально связано с подтверждаемым действием. Доставка указания раннером считается состоявшейся не по факту записи, а по активности потока после `tool_result` in-flight-инструмента; error-события доставку не подтверждают (`docs/architecture/decisions/0007-dostavka-ukazanij-push-delivered.md:17`). Общий корень обоих принципов: проверка обязана измерять то, что она заявляет. Сторож, который нельзя пройти честно, измеряет периметр участника вместо синхронности артефакта; delivered без каузальной связи измерял бы факт записи вместо факта доставки. В обоих случаях лечение одно — привести конструкцию проверки в соответствие с тем, что она обещает гарантировать.
